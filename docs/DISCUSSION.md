# 待建设能力：需要你决策的清单

这份文档是你和我之间的决策接口。[能力地图](MIGRATION-OVERVIEW.md)说明了现状，[`pending/`](pending/) 下的 12 份文档给出了每个领域的技术分析，这里把它们收敛成一组可以逐条回答的问题，并给出我的判断。

## 怎么用

问题按**杠杆率**排序，不是按领域排。排在前面的问题，一个答案能决定好几个领域的走向；排在后面的是单领域的参数，可以晚一点再说。

每个问题都设计成能用一两句话回答。你不需要一次答完——按梯队来，第一梯队答完我就能给出一版具体的建设排期。

我在每一节末尾标了**我的倾向**。这些是基于公开技术常识和本仓库审读结论的判断，不是定论，你有更多内部信息，可以直接推翻。

## 零、在回答任何问题之前：先填 profile

这件事成本接近零，但收益最大，而且会自动回答下面一半的问题。

[`hardware-profiles/_TEMPLATE.yaml`](../hardware-profiles/_TEMPLATE.yaml) 是一张空白的硬件能力清单，照着 [`cuda-reference.yaml`](../hardware-profiles/cuda-reference.yaml) 填。填完之后：

- 已建成的 9 个 skill 立刻可用——它们不含任何硬编码的厂商信息，全部读这份 profile
- 每个 `_status: unknown` 和 `null` 都是一个暴露出来的能力缺口，填的过程本身就是一次盘点
- 填不出来的字段直接留 `null` 并把 `_status` 标成 `unknown`，skill 会走降级路径并提示缺什么，比填一个猜的值安全

**不要为了填满而猜。** 一个错的 `memory_bandwidth_gbps` 会让所有 roofline 判定系统性偏向一边，比留空危害大得多。

## 第一梯队：一个答案解锁一片

这三组问题各自卡着多个领域。建议优先回答。

### 1. 你的 profiler 能导出什么？

这是**整个仓库最大的单点阻塞**。下列八处的输入都是性能数据：性能拆解、多流并发的效果验证、性能数据采集、图融合机会排序、权重预取的判据、子图融合的诊断前提、融合算子的收益评估、量化的收益评估。格式一天不定，八个地方都要各自打补丁。

| # | 问题 | 为什么重要 |
|---|---|---|
| 1.1 | 运行时能否在**单个 kernel 粒度**上给出开始与结束时间戳？还是只能给到整个 forward 一级？ | 这是地板。只有 forward 级计时的话，上面八处全部停摆，第一件要做的事是在运行时里补 kernel 级计时 |
| 1.2 | 芯片是否通过 PrivateUse1 接入 PyTorch，`torch.profiler` 能否拿到设备侧事件？ | 如果能，适配工作量可能是零——现成的 chrome trace 适配器直接可用 |
| 1.3 | 硬件有没有性能计数器（PMU）？驱动暴露读取接口了吗？ | 决定终局高度。没有计数器，「访存受限还是计算受限」「roofline」「融合收益预估」这三类结论**永久得不出来**，相关分析只能退化为按耗时排序 |
| 1.4 | 产物是什么格式（chrome trace / CSV / 自有二进制）？列名和时间单位是什么？ | 决定适配器怎么写。是 CSV 的话，填一下 `profiler.kernel_table_columns` 就能复用现成实现 |
| 1.5 | 采集时能否保留 step 标注，把设备 kernel 关联回主机侧的 step？ | 决定能否按 step 切分，也就是能否剔除首步编译开销、识别步间抖动 |
| 1.6 | 多卡采集时各 rank 的时间戳是否同源可比？ | 决定能否把「通信慢」归因到具体的慢卡 |

**我的倾向**：先答 1.1 和 1.2。本仓库已经把[统一 kernel schema 与适配层](../tools/profiler_adapter/README.md)建好了，chrome trace 和 CSV 两种格式的适配器都能跑。如果 1.2 的答案是「能」，这一整块可能今天就通了。完整分析见 [性能数据采集](pending/perf-profiling.md)。

### 2. 你的通信后端支持到哪一步？

卡着多卡的一切：并行实施、通信与计算重叠、多卡精度排查、MoE 能否跑。

| # | 问题 | 为什么重要 |
|---|---|---|
| 2.1 | 有没有 `torch.distributed` 后端？支持哪些算子？ | 整条分布式路线的地板 |
| 2.2 | **有没有支持不等长切分的 `all_to_all_single`？** | 当前最关键的单点。只有等长版本的话，MoE 的专家并行直接不成立，而主流大模型大多是 MoE |
| 2.3 | 规约类算子原生支持 `bfloat16` 吗，还是走软件模拟？ | 走模拟的话慢到不能用于训练，而现在的大模型训练默认就是 bf16 |
| 2.4 | 支持 `async_op=True` 并返回工作句柄吗？ | 决定通信与计算能否重叠，这是多卡性能的主要来源之一 |
| 2.5 | 规约顺序是否确定？有没有可开关的确定性模式？ | 决定分布式训练能否复现，直接关联训练精度三件套 |
| 2.6 | 有没有把集合通信与矩阵计算编进同一个算子的能力？ | 通用生态在这里是真空，这是你有机会做出差异化的地方 |

**我的倾向**：2.2 优先于其余所有通信问题。另外明确一点——**不要自己写并行切分层**，Megatron-LM 和 vLLM 已经把那几万行写完并验证过了，重写拿不到任何差异化。把力气放在后端。理由展开在[并行切分实施](pending/parallel-impl.md)。

### 3. 你有任何形式的张量 dump 能力吗？

卡着四个领域：训练精度三件套，加上推理精度诊断。

| # | 问题 | 为什么重要 |
|---|---|---|
| 3.1 | 现在有任何形式的张量 dump 吗（哪怕只是 runtime 层的裸内存 dump）？ | 决定是从零建还是在已有基础上加一层框架层 |
| 3.2 | 有没有可信的标杆平台（CPU fp32？另一个硬件？） | 没有标杆的话，「与标杆不一致」这个领域不成立，比对能力只能用于自己和自己比 |
| 3.3 | `torch.use_deterministic_algorithms(True)` 在你的后端上实际会发生什么——真切换实现、静默忽略、还是遇到无确定性实现时抛错？ | **静默忽略是最坏的情况**：你以为开了确定性，其实没开，所有基于它的排查都建立在错误前提上 |
| 3.4 | 训练主路径是 eager 还是图模式为主？ | 图模式下三种 Python 插桩方式全部失效，必须先建一个「诊断时强制 eager」的开关 |
| 3.5 | 最先要解决的是哪一类问题——不可复现 / NaN / 对不齐标杆？ | 决定工具第一阶段的默认采集配置往哪边偏 |

**我的倾向**：三个精度领域**共用同一套底座，应该一次性建，不要分三次**。而且第一阶段可以很轻——基于 PyTorch hook 的统计摘要 dump，不落完整张量，就能覆盖相当一部分场景。路线图见 [精度工具栈建设方案](pending/_precision-toolchain.md)。另外 3.3 值得你现在就去实测一下，这个答案经常和文档上写的不一样。

## 第二梯队：决定某条路线能否成立

这些问题各自决定一个领域是否立项。答「没有」也是有价值的答案——可以直接关掉那个领域，不用再占注意力。

| # | 问题 | 领域 | 答「没有」的后果 |
|---|---|---|---|
| 4.1 | 能从哪一层导出计算图——`torch.fx`、Dynamo 捕获的 graph、还是自研编译器的 IR dump？ | [图融合机会分析](pending/graph-fusion-analysis.md) | 领域不成立。算法部分完全通用且现在就能实现，唯一的硬阻塞就是拿不到图 |
| 4.2 | 有没有框架可调用的**跨算子**预取 API？语义是什么（搬到哪一级缓存、栅栏怎么表达）？ | [权重预取](pending/weight-prefetch.md) | 领域不成立，退化为 roofline 分析。注意 `cudaMemPrefetchAsync` 不是对位物，那是统一内存的页迁移 |
| 4.3 | 编译器有没有「标注一段范围、生成单个 kernel」的能力或规划？ | [子图二进制融合](pending/subgraph-fusion.md) | 领域不成立，退化为图捕获，而图捕获已经建好了 |
| 4.4 | 现在有哪些融合算子？能给一份清单和参数契约文档吗？ | [融合算子替换](pending/fused-op-substitution.md)、[推理精度诊断](pending/infer-precision-debug.md) | 流程可用但无算子可换。这份清单同时是推理精度排查的必要输入 |
| 4.5 | 支持哪些量化格式？权重需要特殊内存布局吗？缩放因子是什么粒度？ | [量化接入](pending/quantization.md) | 无法判断量化路线怎么走 |
| 4.6 | 有端侧产品线吗？ | [端侧部署](pending/edge-deployment.md) | 答「没有」就直接关闭，文档留作决策记录 |

**我的倾向**：

- 4.3 我建议**现在就答「暂不做」**。子图二进制融合只在 decode、形状固定的前提下生效，需要编译器团队专门投入。同样的投入放在「提高图捕获覆盖率」「补关键融合算子」「权重量化」任一条上，收益都更确定、适用面都更广。只有当那三条都做到位、性能数据仍显示设备侧调度占大头时，它才值得排期。
- 4.6 如果没有端侧产品线，**直接关闭**。它和其余 20 个领域不共享任何基础——没有 Python 运行时、提前编译、功耗和包体积进入目标函数。把云侧 skill 改写成端侧版本，改出来的东西不会对。
- 4.4 这份清单是**你唯一无法外包给我的输入**。方法论我可以写，算子契约只能来自你的算子团队。

## 第三梯队：单领域的具体参数

这些可以等前两个梯队有结论后再答，或者等真正要建那个领域的时候再答。

**性能相关**
- 单次 kernel 启动开销实测是多少微秒？（决定小算子融合值不值得做）
- 当前 decode 的气泡占比是多少？单步有多少个 kernel？（区分主机侧下发开销和设备侧调度开销，这两者的解法完全不同）
- 同一个算子在不同次执行中的 kernel 名是否稳定？名字里带不带 shape 或地址？（名字不稳定的话按名称聚合会失效）
- 计数器的「利用率」分母是峰值规格还是当前时钟下的理论值？（分母搞错会让受限判定系统性偏向一边）
- 视图类算子（permute / reshape / contiguous）在你的后端会不会产生实际拷贝？

**精度相关**
- GEMM 默认用什么累加精度？能否强制 fp32 累加？（这一条的答案往往能直接解释掉大半的误差）
- 逐元素数学函数（exp / erf / tanh / rsqrt）是精确实现还是近似？误差界多少？
- 融合算子有没有可切换的朴素实现作为对照？
- 有没有 kernel autotune / JIT 调优缓存？能否钉死配置？
- 有没有 racecheck 类的竞态检测工具？
- 模型实现里哪些地方用 inf 或极大负数作哨兵（mask、top-k 填充、MoE 容量溢出）？（这份白名单工具无法自动推断）

**工程上下文**
- 训练框架用的是什么（Megatron-LM / torchtitan / 自研）？
- 目标模型结构是哪几类（稠密 / MoE / 多模态）？
- 先上推理还是先上训练？（决定先对接 vLLM 还是 Megatron-LM）
- decode 延迟目标是多少？当前离目标差多远？

## 如果你只想回答三个问题

按解锁面积排：

1. **`torch.profiler` 能不能拿到你的设备侧 kernel 事件？**（第 1.2 题）——能的话八个地方一起通
2. **有没有支持不等长切分的 `all_to_all_single`？**（第 2.2 题）——决定 MoE 这条路通不通
3. **`torch.use_deterministic_algorithms(True)` 实测是什么行为？**（第 3.3 题）——成本是跑一个十行脚本，但「静默忽略」这个答案会让你省下一整轮白跑的排查

## 我建议的推进顺序

不含时间估计，只是依赖顺序。

**第一步，填 profile。** 零成本，立刻激活 9 个 skill，顺带暴露缺口。

**第二步，打通 profiler 适配器。** 杠杆率最高的一件事。统一 schema 和两个参考适配器已经写好并验证过了，缺的只是接上你的产物格式。通了之后，性能拆解和多流验证立刻可用，另外四个待建领域也有了输入。

**第三步，核查通信后端。** 这一步主要是「查清楚」而不是「建」，但它决定多卡路线怎么走，而且越早知道越好——如果 `all_to_all_single` 缺不等长支持，这个结论影响到模型选型，拖到后期发现代价很大。

**第四步，精度工具栈第一阶段。** 基于 hook 的统计摘要 dump。三个精度领域共用，一次投入解锁三块。

**第五步，整理融合算子清单与参数契约。** 这件事看起来像文档工作，实际上它同时是融合算子替换、推理精度诊断、KV cache 适配三个领域的输入。

**建议明确不做的**：端侧部署（除非有产品线）、子图二进制融合（优先级低于上面五条）、自建并行切分层（对接成熟实现）。

## 关于「迁移」这个词

你最初的要求是迁移通用 skill、保留硬件绑定的 skill 并讨论怎么迁。执行中发现源项目的许可证明文禁止把它的内容用于非华为处理器，所以实际交付从「改写迁移」调整成了「按相同能力领域独立编写」，依据和边界记在 [LICENSE-CONSTRAINT.md](LICENSE-CONSTRAINT.md)。

这对本文档的影响是：上面所有问题问的都是「**这个能力在你的芯片上怎么建**」，而不是「这个 skill 怎么从昇腾搬过来」。实际损失比预想的小——这类 skill 的价值主体是方法论，而方法论来自公开文献；真正专有、无法独立获得的那部分（厂商算子目录、错误码本、特定工具的操作契约），恰好也是迁移之后用不上的部分。

如果你希望走授权路线直接复用源仓内容，LICENSE-CONSTRAINT.md 末尾列了几个可能的方向，但那需要你的法务介入。
