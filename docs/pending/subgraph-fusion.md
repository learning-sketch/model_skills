# 子图二进制融合

## 一句话结论

这个优化想解决的是「kernel 太多、每个太小，调度开销占了大头」。在决定建设之前要先分清：你的开销是在**主机侧下发**还是**设备侧调度**。前者用图捕获就能解决，已经有了；后者才需要把子图编成单个 kernel，是另一回事。搞错了会花大力气解决一个本来就不存在的问题。

## 先分清两种开销

decode 阶段每一步要执行成百上千个 kernel，每个 kernel 的计算量都很小。此时「跑 kernel 之外的时间」可能超过「跑 kernel 的时间」。但这个开销有两个来源，处置方式完全不同。

**主机侧下发开销。** CPU 要为每个 kernel 做参数打包、入队、同步。当 kernel 执行得比 CPU 下发还快时，设备就会空等。表现是：性能数据里设备忙时远小于墙钟，气泡占比高。

**设备侧调度开销。** 每个 kernel 启动时要分配资源、初始化上下文，结束时要回收、写回结果。这部分在设备上发生，即使 CPU 下发得再快也省不掉。此外，相邻 kernel 之间的中间结果必须经过显存往返，无法留在片上。

| 开销类型 | 怎么识别 | 解决手段 | 本仓库现状 |
|---|---|---|---|
| 主机侧下发 | 气泡占比高，且 CPU 侧 profiling 显示下发线程忙 | 图捕获（一次捕获、多次重放） | [图模式](../../skills/model-infer-graph-mode/SKILL.md) 已建成 |
| 设备侧调度 | 气泡占比低（设备一直忙），但 kernel 数量巨大、单个 kernel 耗时接近启动开销量级 | 把多个 kernel 编成一个 | 本文档讨论的内容 |

**先做诊断再决定。** 用性能拆解的 step 概览看气泡占比：

- 气泡占比高（> 20%）→ 问题在主机侧，先把图捕获用起来，这个领域暂不需要
- 气泡占比低但整体慢，且单步 kernel 数量上千 → 可能是设备侧开销，继续往下看
- 两者都不是 → 瓶颈在 kernel 本身，去做算子优化

## 设备侧融合的技术路线

假设诊断结论确实是设备侧开销，有三条路线。

### 路线一：编译器自动融合

现代深度学习编译器会自动把相邻的逐元素算子、归约算子融合成一个 kernel。这是现成能力，不需要你做什么。

局限在于：**它通常不跨越库调用。** 矩阵乘一般是调用高度优化的库实现（CUTLASS 之类），编译器不会把它和前后的逐元素算子编到一起。而 LLM 里耗时的恰恰是矩阵乘。所以自动融合能消掉一批小算子，但消不掉主干。

判断你当前受益多少：看性能数据里「逐元素」桶的占比。占比低（< 5%）说明自动融合已经做得不错；占比高说明还有空间，但这是编译器配置问题，不是要建新能力。

### 路线二：手写融合算子

把一段固定的计算模式（比如 `RMSNorm + 矩阵乘 + SwiGLU`）手写成一个 kernel。中间结果留在寄存器或共享内存里，不走显存。

这是收益最确定的路线，也是业界主流做法。FlashAttention 就是这个思路的典型。代价是每个模式都要单独写、单独调优、单独维护。

这条路线归属于[融合算子替换](fused-op-substitution.md)，不在本文档范围。

### 路线三：标注范围、编译器生成单个 kernel

由开发者标注「这一段子图编成一个 kernel」，编译器负责代码生成。这是本文档讨论的能力。

相比路线二的优势是不用手写 kernel；相比路线一的优势是能跨越库调用边界，且范围由人控制。

CUDA 生态里**没有这个能力的公开一等公民 API**。最接近的形态是所谓 megakernel / persistent kernel——一个常驻 kernel 内部用 grid 级同步分隔多个计算阶段。近年有推理引擎用这个思路优化 decode 延迟，但都是手写实现，不是编译器标注生成。

## 这条路线的硬约束

如果你的编译器团队要做这个能力，有几条约束是结构性的，不是实现问题：

**动态形状基本不可能支持。** 编译期要确定整段子图的资源分配（寄存器、共享内存、同步点），形状不确定就算不出来。所以这类优化通常只能用在形状固定的阶段——对 LLM 推理来说就是 decode，prefill 的序列长度每次都变，用不了。

**范围内不能有数据依赖的控制流。** 如果子图里有「根据某个张量的值决定走哪个分支」，就没法编成一个静态的 kernel。

**资源上限会限制范围大小。** 融合的算子越多，需要的寄存器和共享内存越多。超过硬件上限时，占用率（occupancy）会下降，可能反而变慢。所以范围不是越大越好，存在一个最优点，需要实测找。

**和图捕获互斥还是兼容，取决于实现。** 这一点要问你的编译器团队。如果互斥，就要在两种优化之间二选一，而图捕获的通用性更好。

## 如果要建设，方法论部分是这样的

这部分与具体实现无关，有了能力之后可以直接用。

**第一步，选范围。** 从小开始，不要一上来就圈整个模型。推荐顺序：先圈一个结构清晰、内部算子多、没有控制流的模块（比如单个 FFN 或单个 attention 块），验证有效后再逐步扩大。

**第二步，筛查排除项。** 在圈定范围后、实施之前，逐项检查：范围内有没有动态形状？有没有数据依赖的控制流？有没有编译器不支持的算子？有没有需要主机侧参与的操作？任何一项命中，要么缩小范围，要么放弃。

**第三步，强制 A/B 对比。** 这类优化的收益高度依赖具体模型和配置，不能假定一定有效。开关前后各采一次性能数据，对比墙钟和 kernel 数量。多次运行取中位数，因为这类优化的收益往往在噪声量级附近。

**第四步，看负面信号。** 范围扩大后如果出现这些情况，说明过了最优点：编译时间显著变长；显存占用上升（寄存器溢出到显存）；单个融合 kernel 的耗时超过了它替代的所有 kernel 之和。

## 建议

**除非诊断明确指向设备侧调度开销，否则不建议优先建设这个能力。**

理由是投入产出比。这条路线需要编译器团队投入，而且只在 decode 这一个阶段、形状固定的前提下生效。同样的工程投入放在以下任一方向，收益更确定、适用面更广：

1. 把图捕获的覆盖率做高（解决主机侧开销，通用）
2. 补齐关键模块的手写融合算子（解决访存往返，收益最大）
3. 权重量化（减少搬运量，对 decode 近乎线性加速）

只有当上面三条都做到位、性能数据仍然显示设备侧调度占大头时，这个能力才值得排期。

## 需要你拍板的问题

| 问题 | 回答后能解锁什么 |
|---|---|
| 当前 decode 的气泡占比是多少？单步有多少个 kernel？ | 决定问题在主机侧还是设备侧，这是前提 |
| 你的芯片单个 kernel 的启动开销量级是多少（微秒还是亚微秒）？ | 启动开销小的话，设备侧融合的收益空间本来就有限 |
| 你的编译器有没有「标注范围生成单 kernel」的能力或规划？ | 决定这条路线是否可行 |
| 该能力与图捕获是否互斥？ | 互斥的话要做取舍，不互斥才能叠加 |
