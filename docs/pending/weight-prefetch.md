# 权重预取

## 一句话结论

这个优化的价值真实存在，但**它依赖的原语在 CUDA 生态里没有公开对应物**。在决定是否建设之前，先回答一个问题：你的芯片有没有「跨算子的、以数据依赖为栅栏的片上缓存预取」能力。没有的话，这个领域不成立，它的价值会被融合算子内部的异步搬运吸收掉。

## 这个优化在解决什么问题

LLM 的 decode 阶段有一个结构性特征：批量很小（极端情况下是 1），但每一步都要把整个模型的权重从显存读一遍。此时算术强度极低——读一个 `[4096, 4096]` 的 bf16 权重要搬 32 MB，而实际计算量只有 `1 × 4096 × 4096` 次乘加。瓶颈完全在显存带宽上，计算单元大部分时间在等数据。

如果能在执行这个矩阵乘**之前**，趁设备正在做别的（不占带宽的）计算时，把权重提前搬进片上缓存，就能把这段访存延迟藏起来。

关键在于「提前多久」。太早，权重在缓存里被别的数据挤掉；太晚，没藏住。所以需要一个能表达「在某个张量就绪之后、在目标算子之前」的栅栏。

---

## CUDA 生态里有什么、没有什么

这一节是本文档的核心判断，容易被误判，所以说细一点。

**`cudaMemPrefetchAsync` 不是对应物。** 它作用于统一内存（Unified Memory）的页迁移，解决的是「这块内存当前的物理位置在主机还是设备」。它不负责把显存里的数据搬进片上缓存。用它做权重预取是找错了层级。

**L2 驻留策略（`cudaAccessPolicyWindow`）接近但不等同。** 它可以把一块显存区域标记为优先驻留在 L2，并为此预留一部分 L2 容量。这是**驻留策略**，不是**定时预取**——它影响的是"数据一旦进了 L2 就别被挤出去"，不解决"什么时候开始搬"。对于反复访问同一块数据的场景有效，对于「每层权重各读一次」的 decode 场景帮助有限。

**`cp.async` / TMA 是真正的异步搬运原语，但作用域不对。** Ampere 引入的 `cp.async`、Hopper 引入的 TMA，都是从全局内存异步搬到共享内存，这正是"提前搬"的机制。但它们是**算子内部**的指令，由 kernel 作者在写 kernel 时使用。现代的 FlashAttention 和 GEMM kernel 内部大量使用这类流水，把本次迭代的计算与下次迭代的数据搬运重叠起来。

所以准确的说法是：**异步预取这件事在 CUDA 里一直在做，但做在 kernel 内部，不是跨算子的框架级 API。** 一个框架层面的 `prefetch(weight, depend_on=some_tensor)` 这样的调用，CUDA 没有提供。

**多流手工拷贝是个陷阱。** 看起来可以在另一条流上发一个 memcpy 把权重"搬一下"，但搬到哪？搬到另一块显存还是在显存里，没有进片上缓存，纯属浪费带宽。除非你的芯片提供了显式的缓存填充指令。

## 对你的芯片要问清楚的三件事

| 能力 | 问题 | 如果有 | 如果没有 |
|---|---|---|---|
| 算子内异步搬运 | 写 kernel 时能否异步地从显存搬数据到片上缓存，并与计算重叠？ | 这是现代 GEMM / attention kernel 的基础，应该已经在你的算子库里用了 | 你的算子库性能会有系统性损失，这是比预取更优先的问题 |
| 跨算子预取 | 有没有框架可调用的 API，能在算子 A 之后、算子 B 之前触发对 B 权重的预取？ | 这个领域成立，可以建设 | 领域不成立，见下文的替代路径 |
| 缓存驻留控制 | 能否把某块数据钉在片上缓存里？ | 对反复访问的小权重（如 MoE 的路由器）有价值 | 无影响 |

## 现在就能用的部分

不管上面三个问题的答案是什么，**判断"哪些算子值得做访存优化"这件事现在就能做**，它只依赖性能数据。

判据如下。前两条需要硬件计数器（见 [性能数据采集](perf-profiling.md)），后两条只需要时间数据。

| 判据 | 含义 | 阈值参考 |
|---|---|---|
| 访存利用率高、计算利用率低 | 典型的访存受限算子，是候选 | 访存 > 0.6 且计算 < 0.3 |
| 实测耗时接近理论访存下限 | `权重字节数 / 显存带宽`，若实测接近这个值说明确实卡在搬数据 | 实测 / 理论 < 1.5 |
| 前序算子不是访存密集的 | 预取需要一个带宽空闲的窗口。前序也在抢带宽就没有窗口 | 看前序算子的分类 |
| 前序算子有足够执行时间 | 窗口太短，搬不完 | 前序耗时 > 权重搬运理论耗时 |

**第三条最容易被忽略，也最容易做错。** 很多人选了一个访存受限的算子做预取，但它前面紧挨着另一个访存受限的算子，两者抢带宽，结果目标算子没变快、前序反而变慢了。选窗口时必须看前序的性质，不能只看目标。

理论访存耗时的计算：

```
理论耗时(us) = 权重字节数 / (显存带宽 GB/s × 1000)

权重字节数 = 各维度乘积 × 每元素字节数
  bf16 / fp16 : 2 字节
  fp8 / int8  : 1 字节
  int4        : 0.5 字节
```

显存带宽从 `profile.devices.models[].memory_bandwidth_gb_s` 取。注意这是标称峰值，实际可达通常是它的 70% 到 85%，估算时留出余量。

## 没有跨算子预取时的替代路径

如果第二个问题的答案是"没有"，这部分价值并不会完全丢失，而是转移到三个别的地方：

**第一，融合算子内部的流水。** 把相邻的访存受限算子融成一个 kernel，在 kernel 内部用异步搬运做软件流水。这是收益最大的路径，但需要写 kernel。

**第二，多流重叠。** 把访存密集的工作和计算密集的工作放到不同的流上并发执行，让访存的那条流在计算流忙的时候占用带宽。这不如预取精确，但不需要新硬件能力，用[多流优化](../../skills/model-infer-multi-stream/SKILL.md)就能做。注意要用重叠率验证是否真的生效。

**第三，减少要搬的数据量。** 量化是最直接的手段——权重从 bf16 降到 int8，搬运量直接减半，对访存受限算子几乎是线性加速。对 decode 阶段这通常比任何预取技巧都有效。

**这三条里，第三条的性价比通常最高。** 如果你的目标是改善 decode 延迟，优先做权重量化，而不是建设预取能力。

## 如果要建设

假设你的芯片有跨算子预取原语，建设的内容是：

**改动涉及的子系统**：推理框架的模型层（插入预取调用点）、配置系统（开关与预取量参数）、性能分析侧（验证预取是否生效）。模型层的改动是侵入式的——预取调用必须插在模型 forward 的特定位置，依赖对模型结构的理解，没法做成完全透明的优化。

**主要风险**：

- **预取量设置过大会抢带宽，让前序算子变慢。** 必须从保守值起步，按实测调整，而不是一上来就按权重全量设置
- **图模式下依赖关系的表达。** 如果走图捕获路径，预取的"栅栏"必须是图里真实存在的数据依赖边，不能是运行时才确定的顺序。依赖表达错了，编译器可能把预取重排到无效的位置，而且不会报错
- **收益难以归因。** 预取生效与否只能通过性能数据间接判断，要有一个可靠的 A/B 对比流程

**必须的工程纪律**：所有预取调用用开关保护、默认关闭；一次只验证一个预取点；每次改动都做开关前后的性能对比，至少要看到目标算子变快**且**前序算子没变慢。

## 需要你拍板的问题

| 问题 | 回答后能解锁什么 |
|---|---|
| 你的芯片有没有框架可调用的跨算子预取 API？语义是什么（搬到哪一级缓存、栅栏怎么表达）？ | 决定这个领域是否成立。有的话可以直接开始建设 |
| 你的算子库里，GEMM 和 attention 内部有没有用异步搬运做软件流水？ | 如果没有，这是比预取优先级更高的事 |
| 你的 decode 延迟目标是多少？当前离目标差多远？ | 决定是否值得投入。如果量化已经能满足目标，预取不必做 |
| 你的 profiler 能否给出每个 kernel 的访存带宽利用率？ | 决定上面的判据能不能自动化。不能的话只能靠理论估算加人工判断 |
