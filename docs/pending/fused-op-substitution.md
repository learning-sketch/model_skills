# 融合算子替换

## 一句话结论

流程本身完全通用，卡的不是方法而是**你有没有一个成规模的融合算子库**。而且这件事有个反直觉的建议：不要自己定义算子目录，**照着 vLLM / SGLang 这类主流推理引擎的算子集合来建**，因为模型代码是按它们的接口写的。

## 这件事在做什么

模型代码里写出来的是一串独立的小算子：先 RMSNorm，再矩阵乘，再激活，再矩阵乘。每个算子都要从显存读输入、往显存写输出。中间结果来回搬运的开销，往往超过计算本身。

融合算子把这一串编成一个 kernel，中间结果留在片上，不落显存。典型的收益来自两处：省掉的显存读写，以及省掉的 kernel 启动次数。

这个领域的工作是：**识别模型代码里可以被融合算子替换的计算模式，替换，然后验证精度和性能。**

---

## 收益怎么估

替换之前先估一下值不值得。

```
省下的显存流量 = Σ(被消去的中间张量字节数) × 2        # 一次写 + 一次读
理论节省时间   = 省下的显存流量 / 显存带宽
省下的启动次数 = 被替换的算子数 - 1
```

举例：一个 `[batch, seq, hidden]` 的中间张量，bf16，batch=1、seq=1（decode）、hidden=4096，那它只有 8 KB。消去它省下的流量微不足道。同样的张量在 prefill 阶段 seq=4096 时是 32 MB，消去它就很可观。

**所以同一个融合，在 prefill 和 decode 阶段的收益可能差两个数量级。** 不要用一个阶段的测试结果去推断另一个阶段。

另一类收益来自启动次数。decode 阶段单步 kernel 数量很大，如果你的单 kernel 启动开销是微秒量级，消去几百次启动就是几百微秒，这在 decode 延迟里是实打实的。

## 工作流

### 第一步：拆模块

从整网开始逐层展开，拆到可替换的计算链路粒度：

```
整网
 └─ Embedding
 └─ Decoder Layer × N
     ├─ 输入归一化
     ├─ Attention
     │   ├─ QKV 投影
     │   ├─ 位置编码
     │   ├─ KV cache 读写
     │   ├─ 注意力计算
     │   └─ 输出投影
     ├─ 残差连接
     ├─ 后归一化
     └─ FFN（或 MoE）
         ├─ 门控 / 路由
         ├─ 上投影
         ├─ 激活
         └─ 下投影
 └─ 最终归一化
 └─ LM Head
```

拆的时候对每个模块记四件事，它们决定了能不能替换：

| 要记的信息 | 为什么重要 |
|---|---|
| prefill 与 decode 的行为差异 | 很多融合算子只在其中一个阶段适用 |
| 张量布局约定 | 融合算子对输入布局有要求，不匹配就要加转换，可能把收益吃掉 |
| 中间结果有没有被别处消费 | 被消费了就不能消去，融合范围要缩小 |
| 是否涉及量化 | 量化路径和非量化路径的融合算子通常是两套 |

**第三条最容易出错。** 看起来是一串线性的算子，但中间某个输出被残差连接或别的分支用了，融合后那个值就没了。替换前必须确认中间结果的消费者。

### 第二步：查算子库

从 `profile.kernels.*` 查你实际有什么。**这一步要查实际文档，不能按名字猜语义。**

同名算子在不同库里的语义差异是精度问题的常见来源。举几个真实存在的分歧点：

- 缩放因子（`1/sqrt(d)`）是算子内部乘，还是要调用方先乘好
- mask 的约定是「True 表示保留」还是「True 表示屏蔽」
- RMSNorm 的 epsilon 加在平方根内还是外
- RoPE 的旋转是相邻配对还是半分配对
- 激活函数的 gate 和 up 在输入张量里哪个在前

这些都不会报错，只会让结果悄悄偏掉。所以每个算子第一次用之前，先用小张量和朴素实现对一遍。

### 第三步：替换与验证

**一次只换一个模块。** 换完立刻验证，通过了再换下一个。批量替换后出了问题，定位成本会高得多。

每次替换的验证包含三项：

| 验证项 | 怎么做 | 通过标准 |
|---|---|---|
| 数值对齐 | 同样输入，对比替换前后的模块输出 | bf16 下最大相对误差通常在 1e-2 量级，超出要查 |
| 端到端精度 | 跑固定 prompt，对比生成文本 | 短输出应完全一致；长输出允许在采样引入随机性后发散 |
| 性能 | 对比替换前后的模块耗时 | 必须变快。没变快说明融合没生效或收益被布局转换吃掉了 |

**第三项不通过时不要默认保留替换。** 融合算子如果因为布局不匹配需要前后加转换，净收益可能是负的。这种情况应该回退，并记录「这个算子需要配合布局改造才有收益」。

### 第四步：记录失败

替换不成功的情况要记下来，这比成功的更有价值：

- 哪个模式找不到对应算子 → 这是算子库的需求清单
- 哪个算子有约束导致用不了（形状限制、dtype 限制、不支持某种 mask）→ 这是算子库的改进清单
- 哪个算子语义对不上 → 这是文档需要澄清的地方

## 为什么建议照着主流引擎的算子集合建

如果你要从零规划算子库，有一个现实考虑：**模型代码是按主流引擎的接口写的。**

当一个新模型发布时，社区的推理实现会很快出现在 vLLM、SGLang 这类引擎里。那些实现调用的是一组事实上的标准算子接口。如果你的算子库接口与之对齐，接新模型时改动量很小；如果你自定义了一套，每接一个模型都要重新适配一遍。

按这个思路，建议的优先级顺序是：

| 优先级 | 算子 | 理由 |
|---|---|---|
| 最高 | 变长 attention（prefill） | 没有它长 prompt 的显存是 O(S²)，直接卡住可用性 |
| 最高 | 分页 attention（decode） | 没有它 KV cache 管理无法高效，见 [KVCache](../../skills/model-infer-kvcache/SKILL.md) |
| 高 | 融合的归一化 + 残差 | 调用频次极高，每层两次 |
| 高 | 融合的激活（SwiGLU 一类） | 消去一个与 hidden 同尺寸的中间张量 |
| 高 | 位置编码 | 调用频次高，且语义分歧多，自己实现容易出错 |
| 中 | 分组矩阵乘 | MoE 的基础，没有它 MoE 性能无从谈起 |
| 中 | 量化矩阵乘 | 配合量化，对 decode 收益大 |
| 低 | 更深度的融合（如 norm + 矩阵乘 + 激活 三合一） | 收益递减，且组合爆炸，维护成本高 |

## 需要你拍板的问题

| 问题 | 回答后能解锁什么 |
|---|---|
| 你现在有哪些融合算子？能给一份清单和各自的参数契约文档吗？ | 这是填 `profile.kernels` 的直接输入，填完这个领域就能用 |
| 算子接口是自定义的，还是对齐了某个主流引擎？ | 决定接新模型的成本，也决定要不要现在调整接口 |
| 有没有算子的参考实现或单测，可以用来验证语义？ | 决定第二步的语义核对能否自动化 |
| 你的目标模型结构是哪几类（稠密 / MoE / 多模态）？ | 决定算子库的建设优先级 |

## 知识来源

- 算子融合减少显存往返的收益模型：FlashAttention 论文（Dao et al., 2022）的 IO 复杂度分析
- 分页 attention 的设计：vLLM 论文 "Efficient Memory Management for Large Language Model Serving with PagedAttention" (Kwon et al., 2023)
- 主流推理引擎的算子接口：vLLM、SGLang、FlashInfer 的公开源码与文档
- RoPE 的两种配对方式、RMSNorm 的 epsilon 位置等语义分歧：各开源实现的公开代码对比
- 变长（varlen）注意力的接口约定：FlashAttention 开源实现的公开 API
