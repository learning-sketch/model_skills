# 性能数据采集

> 组 1 的根节点。等级 **C**（需要先建设一个专门的底层能力）。

## 一句话结论

**性能数据采集不是一个"分析能力"，而是六个分析能力共用的输入管道；它能导出什么，直接封死了上层的天花板。** 现在最该做的不是把采集建到完备，而是先确认你的运行时处在哪一层，然后把下一层的字段补上去——每补一类字段，解锁的分析是确定的、可以提前算出来的。

## 当前状态

| 现在能做 | 还差什么 |
|---|---|
| 分析侧的统一 schema 与校验逻辑已经写好（[`tools/profiler_adapter/schema.py`](../../tools/profiler_adapter/schema.py)），分析脚本只认这个 schema | 没有任何一个适配器对接你的 profiler。现成的两个适配器只覆盖 chrome trace 与通用 CSV |
| 采集纪律（本文「采集纪律」节）与产物验收流程现在就能执行，与芯片无关 | 不知道你的运行时能不能给出 kernel 粒度的时间戳，以及硬件有没有可读的性能计数器 |
| 拿到符合 schema 的数据后，[`model-infer-perf-breakdown`](../../skills/model-infer-perf-breakdown/SKILL.md) 立刻可用 | `hardware-profiles/` 里 `profiler` 一节全是 `null`，`_status: unknown` |

**本文不要求你先把采集建完再讨论。** 相反，先回答文末的问题，才能判断该建到哪一层。

## 为什么它是整组的瓶颈

性能数据是下列六处的共同输入。它们的实现各不相同，但都只消费同一份 kernel 时间线：

| 消费方 | 状态 | 没有性能数据时退化成什么 |
|---|---|---|
| [性能拆解](../../skills/model-infer-perf-breakdown/SKILL.md) | 已建设 | 整个 skill 跑不起来，它的 Step 0 第一句就是"先归一化输入" |
| [多流优化](../../skills/model-infer-multi-stream/SKILL.md)的效果验证 | 已建设 | **只能靠端到端墙钟判断切流有没有生效**。墙钟变快可能来自任何原因，判断不了是不是并行带来的 |
| [图模式](../../skills/model-infer-graph-mode/SKILL.md)的收益预判与验证 | 已建设 | 它的 `gap_ratio` 判据失效，只能盲目试做；做完也说不清收益来自消除下发还是别的 |
| [图结构与融合机会分析](graph-fusion-analysis.md) | 待建设 | 能找出重复子图，但**排不了序**——不知道哪个子图真的耗时 |
| [量化接入](quantization.md) | 待建设 | "真实生效验证"少掉 kernel 名这条证据，只剩显存和 dtype 两条 |
| [推理精度诊断](infer-precision-debug.md) | 待建设 | 影响较小（精度问题看数值不看时间），但定位"哪一层慢导致超时"时仍需要 |

一个格式不定，六个地方都要打补丁。本仓已经用[适配层](../../tools/profiler_adapter/README.md)把这件事收敛成"写一个适配器"，所以**真正的阻塞只剩采集侧能导出什么**。

## 分层的能力要求

下面三层与 [`schema.py`](../../tools/profiler_adapter/schema.py) 里的 `ANALYSIS_REQUIREMENTS` 一一对应。校验器的判定规则是：某个分析所需字段的**覆盖率低于 50% 即视为不可用**（部分缺失的数据做出来的结论会误导人），所以"有这个字段"指的是绝大多数事件上都有，不是偶尔有。

### T1 · 最低可用

**需要 profiler 提供**：`name`、`start_us`、`duration_us`、`stream_id` 四个必需字段。这是 schema 的硬门槛，缺一项数据根本进不来。

要点：`name` 必须**同一个算子在不同次执行中稳定**（不能带地址、不能带随机后缀），否则按名称聚合会把一个算子拆成几千个；`start_us` 只要求同一份数据内部同源可比，绝对原点随意。

**解锁的分析**（`ANALYSIS_REQUIREMENTS` 中的 2 项）：`气泡（空隙）分析`、`多流重叠率`。此外 schema 之外的两项聚合也成立：按 kernel 名的总耗时排序（Top-N），以及同名 kernel 的耗时离散度。

**此层的一个陷阱**：`stream_id` 是必需字段，所以校验器一定会报"多流重叠率可用"。但如果你的数据里只有一条流，这个分析在语义上是空的——校验器为此专门留了一条警告"只有一个流，多流相关分析无意义"。**schema 层面可用不等于语义上有意义**，报告要连着警告一起读。

**典型实现难度**：只改采集侧。前提是运行时在 kernel 下发/完成处有可挂的回调或事件。若运行时只能给"整个 forward 耗时"这种粒度，这一层就不成立，得先在运行时里补 kernel 级计时。

### T2 · 实用

**需要 profiler 额外提供**：`step_id`、`category`、`device_id`。

| 字段 | 来源通常在哪 | 注意 |
|---|---|---|
| `step_id` | 主机侧的 step 标注事件，按时间区间反推设备 kernel 的归属 | chrome trace 没有原生 step 列，适配器是从 `ProfilerStep#N` 标注反推的；采集时不调 `step()` 这个信息就永久丢失 |
| `category` | 你的 profiler 的 task_type 列，映射到 `compute`/`communication`/`memory`/`host` 四类 | 校验器只把**非 `unknown`** 的算进覆盖率。分不清就填 `unknown`，别硬塞 `compute` |
| `device_id` | 多卡采集时每个 rank 各自的设备号 | 没有它，多卡数据合并后无法分开看 |

`host` 这一类值得单独说：它表示算子掉回主机侧执行，通常意味着该算子缺少设备实现。**这类事件出现本身就是一条性能告警**，不只是分类用。

**解锁的分析**（累计 5 项）：新增 `按 step 切分`、`计算与通信分离统计`、`多卡分别统计`。工程上的直接后果是三件事变得可做：排除首步冷启动后统计稳态、识别 step 间抖动、判断通信是不是真的暴露在关键路径上。

**典型实现难度**：`step_id` 的难点不在采集而在**透传**——要让设备侧事件能关联回主机侧的 step 标注，需要运行时保留下发时的上下文。若运行时完全异步且不带上下文，只能像 chrome trace 适配器那样按时间区间反推，边界处会有误归属。`category` 是纯映射工作，成本最低。侵入性都集中在采集侧，不碰模型代码。

### T3 · 完备

**需要 profiler 额外提供**：`counters`（至少 `compute_util`、`memory_util`）、`block_dim`、`input_shapes`。

计数器有一条硬约束：**取值必须归一化到 0~1**，schema 在 `__post_init__` 里直接抛错。CSV 适配器对 0~100 的百分比做了兼容除以 100，但那是容错不是契约——归一化应该在适配器里按你的 profiler 语义显式做。

**解锁的分析**（全部 8 项）：新增 `访存受限判定`、`并行度是否打满`、`按 shape 聚类`。这一层解锁的是一类**质变的能力**：从"谁慢"变成"为什么慢"，详见后文「硬件计数器的关键性」。

**典型实现难度**：这一层的难度与前两层不是同一个量级，因为它不止是软件问题。
- `block_dim`：如果运行时下发时就知道 grid/block 配置，成本接近零（chrome trace 适配器就是从 `args.grid` × `args.block` 算出来的）
- `input_shapes`：需要框架侧配合记录（PyTorch 侧对应 `record_shapes`），有采集开销，且会显著增大 trace 体积
- `counters`：**依赖硬件 PMU 和驱动的读取接口**。如果芯片没有暴露，这不是写代码能绕过去的；即使暴露了，往往需要 kernel 重放（同一个 kernel 跑多遍采不同组计数器），这会改变时间特性

### 三层汇总

| | T1 最低可用 | T2 实用 | T3 完备 |
|---|---|---|---|
| 字段 | name / start_us / duration_us / stream_id | +step_id / category / device_id | +counters / block_dim / input_shapes |
| 可做的分析 | 2 / 8 | 5 / 8 | 8 / 8 |
| 能回答 | 谁最耗时、设备有没有空等、两条流有没有真重叠 | 稳态是什么样、抖不抖、通信藏住没有、哪张卡慢 | 为什么慢、还有多少空间、值不值得融合或量化 |
| 建设落点 | 运行时的 kernel 计时回调 | 运行时的上下文透传 + 分类词表映射 | 驱动/固件的 PMU 接口 + 框架侧 shape 记录 |
| 主要风险 | kernel 名不稳定导致聚合失效 | step 边界误归属 | PMU 不存在则此层不成立；重放模式下时间数据失真 |

## 技术选项对比

### 选项 A · 基于 PyTorch 内置 profiler 扩展

`torch.profiler` 的产物实际上由两部分拼成：主机侧的算子区间（框架自带的 `RecordFunction` 机制，接上 PyTorch 就有），以及设备侧的 kernel 区间（由 Kineto 这一层从厂商的 tracing 库里拉取，CUDA 侧对应 CUPTI）。**自研芯片要补的只是后半部分**——把你的运行时记录的 kernel 起止时间喂进 PyTorch 的事件流。

| 维度 | 说明 |
|---|---|
| 适用条件 | 你的运行时已有 kernel 级时间戳；芯片通过 PrivateUse1 或自定义后端接入了 PyTorch |
| 直接收益 | `schedule`（warmup/active 窗口）、`record_shapes`、step 标注、主机侧调用栈全部白拿；产物是 chrome trace，本仓的 `chrome-trace` 适配器**开箱即用**，连适配器都不用写 |
| 天花板 | PyTorch 的事件模型里没有硬件计数器的位置。要带计数器只能塞进事件的 `args` 自定义字段，适配器需要特判；也拿不到 kernel 内部的分阶段信息 |
| 侵入性 | 改运行时的 kernel 回调 + 一个 PyTorch 侧插件。**不碰模型代码**，这是它最大的优点 |
| 风险 | PrivateUse1 后端的 profiler 扩展点随 PyTorch 版本变动，升级框架时可能需要跟着改。具体扩展入口以你用的 PyTorch 版本为准，这取决于你的栈接入的方式 |

### 选项 B · 自建基于硬件计数器的采集器

类比 Nsight Compute 那一类工具：在 kernel 边界读 PMU，必要时重放同一个 kernel 多遍以覆盖多组计数器。

| 维度 | 说明 |
|---|---|
| 适用条件 | 硬件有 PMU 且驱动暴露了按 kernel 边界采样的接口。**这一条不满足则此选项直接不成立** |
| 直接收益 | 唯一能回答"访存受限还是计算受限"的路径，T3 的全部价值都在这里 |
| 天花板 | 计数器采集通常要串行化 kernel 执行、禁用并发、重放多遍。**这种模式下的时间数字不能用于优化判断**——它测的不是真实执行 |
| 侵入性 | 集中在驱动/固件层加一个独立 CLI 工具，与 PyTorch 解耦。但也因此拿不到框架语义（哪个 kernel 属于哪个模块、哪个 step） |
| 风险 | 依赖链最长（固件 → 驱动 → 用户态库 → 工具），任何一层没有计划暴露就卡死；计数器语义需要标定，"利用率"的分母是峰值带宽还是当前时钟下的理论带宽，差别很大 |

### 选项 C · 两者结合

timeline 走 A，counters 走 B，离线合并。**这是推荐的终态，本仓 schema 就是按这个结构设计的**（`counters` 是可选字段，缺失只降级不阻断）。

合并的关键是对齐键。两次采集是两次独立运行，必须找到一个稳定的标识把计数器贴回 timeline 事件：

```
对齐键 = (kernel 名, 同名 kernel 在本次运行中的调用序号)
备选   = (kernel 名, input_shapes)     # 当同一算子不同 shape 需要分别看时
```

成立的前提是**两次运行的 kernel 序列完全一致**。实际要做到这点需要：固定随机种子与采样策略、固定输入长度与 batch、关闭算子库的自动调优（autotune 会让不同次运行选到不同 kernel）、关闭任何依赖运行时状态的分支。这些条件里任何一条破了，序号就会错位，而错位的计数器比没有计数器更危险——它会给出看起来合理的错误结论。

| | 选项 A | 选项 B | 选项 C |
|---|---|---|---|
| 能到哪一层 | T2（计数器要塞自定义字段才能到 T3） | T3 的计数器部分，但时间部分不可信 | T3 完整 |
| 框架语义（step/shape/模块） | 有 | 无 | 有 |
| 依赖硬件 PMU | 否 | 是 | 是 |
| 适配器工作量 | 可能为零 | 需要写一个 | 需要写一个 + 一个合并步骤 |
| 建议 | **先做这个**，它能把六个消费方从"完全不可用"拉到"基本可用" | 只在 PMU 确定可用时启动 | 两边都就绪后做，合并逻辑本身不难，难在保证两次运行可对齐 |

## 采集纪律

**这部分与你的 profiler 是什么无关，现在就能执行。** 它决定的是采到的数据可不可信——一份纪律不对的数据，字段再全也会得出错误结论。

### 窗口设置

- [ ] 采集窗口按 `wait → warmup → active` 三段划分。`wait` 跳过冷启动，`warmup` 让 profiler 自身的缓冲分配完成，`active` 才是真正记录的区间
- [ ] `active` 至少 3 步。少于 3 步看不出 step 间离散，"抖动"这件事就无从判断
- [ ] `active` 不宜过大。事件数 × 每事件数百字节，几十万事件就是上百 MB，chrome trace 到 GB 级后浏览器打不开、解析也慢
- [ ] 采完立刻确认 `active` 窗口内各 step 墙钟的变异系数 < 0.1。**超过说明窗口里还混着一次性开销，窗口位置要往后挪**

### 一次性开销必须在窗口外

以下全部是"只发生一次、却可能占掉整个首步"的东西，混进 active 窗口会让均值完全失真：

- [ ] 图编译 / `torch.compile` 的首次编译与任何一次重编译
- [ ] 图捕获（捕获本身的耗时不是执行耗时）
- [ ] 算子库的自动调优。**很多库在首次遇到一个新 shape 时会试跑多个实现**，这会在 trace 里留下一串奇怪的同名 kernel
- [ ] 显存池的首次扩容
- [ ] 通信域建立。首次集合通信里包含 bootstrap，耗时与稳态完全不是一个量级
- [ ] 权重加载、KV cache 块池分配

验收方式：在 trace 里搜编译/调优相关的主机侧事件，应为零。若无法搜（没有主机侧事件），就看 active 窗口第一步是否显著慢于后续——显著慢就是没清干净。

### prefill 与 decode 必须分开采

这两个阶段的 shape、kernel 组成、瓶颈类型完全相反（prefill 的矩阵乘 M 维是 `batch × 序列长度`，decode 只有 `batch`）。混在一份数据里，Top kernel 排序会变成"prefill 的大算子霸榜"，而 decode 的优化机会全被淹没。

- [ ] 优先做两次独立采集：prefill-only（限制只生成 1 个 token）与 decode-only（预先喂满上下文后只采生成阶段）。这是最干净的做法，两份数据各自内部同质
- [ ] 若必须一次采完，用阶段标注区分，再在适配器里切开
- [ ] **本仓 schema 目前没有 `phase` 字段**。现状下只能靠 `step_id` 的区间划分，或者分两次采。若你的 profiler 支持用户自定义标注，这是一个值得给 schema 补字段的地方

### 采集开销会干扰结果

- [ ] 基线对照：同一配置下开 profiler 与不开 profiler 各跑一次端到端。**墙钟差异超过 10% 就说明采集已经改变了被测对象**，此后所有绝对值都要打折，只能看相对关系
- [ ] 按需开启附加项。记录 shape、记录调用栈、记录显存事件逐项都加开销，其中调用栈最贵。不需要就关掉
- [ ] 计数器采集若需要 kernel 重放或串行化，**那一次采集的时间数据直接作废**，只取计数器。不要用同一份数据既看时间又看计数器

### 多卡必须每个 rank 都采

- [ ] 每个 rank 各自采集，产物文件名带 rank 标识，归一化时填 `device_id`
- [ ] 只采 rank0 会产生一类系统性误判：rank0 的集合通信等待时间长 → 看起来"通信慢" → **实际往往是另一张卡算得慢，rank0 在等它**。真正的瓶颈卡根本不在这份数据里
- [ ] 判据：对比各 rank 的 `compute` 总时长。差异超过 10% 是负载不均（切分或数据分布问题），不是通信问题
- [ ] 跨 rank 的时间戳是否同源需要确认。不同源时**不要直接比较绝对时间戳**，改用各 rank 内部的相对时间或 step 边界对齐

### 产物验收

每次采集完、分析开始前，先跑一遍校验：

```bash
cd tools
python -m profiler_adapter.normalize \
  --input <你的产物> --format auto \
  --profile ../hardware-profiles/<你的芯片>.yaml \
  --output /tmp/kernels.jsonl
```

- [ ] 事件总数与时间跨度符合预期（跨度应约等于 active 窗口的墙钟）
- [ ] 字段完整度里，T2 层的三个字段覆盖率 ≥ 50%，否则对应分析会被判为不可用
- [ ] `duration` 为 0 的事件占比很小。占比大说明时间精度不足或**列映射错位**，回头查 profile 的 `kernel_table_columns`
- [ ] 事件分类里 `unknown` 占比低；明知有多卡而 `communication` 占比为 0，说明通信 kernel 没被识别，需要补通信库的命名模式
- [ ] 报告里的「可做的分析」清单，与你这次想回答的问题对得上。对不上就补采，**不要先分析再发现数据不够**

## 硬件计数器的关键性

### 没有计数器时，这些结论永远得不出来

一个 kernel 慢，可能有四种互斥的原因：搬的数据多、算的多、并行度不够、在等别的东西。**只看时间，这四种完全分不开**，而它们对应的优化动作截然不同（融合/预取、量化/换算法、增大批量、查同步点）。缺计数器时，具体失去的是：

| 做不了的事 | 为什么时间数据替代不了 |
|---|---|
| 访存受限 vs 计算受限判定 | 这是 [perf-breakdown](../../skills/model-infer-perf-breakdown/SKILL.md) Step 4 的核心产出，没有计数器时它一律报「未知」而不是猜 |
| roofline 定位 | 要知道算子离屋顶线还有多远，必须同时有达成带宽和达成算力两个坐标 |
| 融合收益预估 | 需要**实际** HBM 读写量。理论访存量会被缓存命中大幅拉低，用理论值估出来的融合收益可能高估数倍，详见[图结构与融合机会分析](graph-fusion-analysis.md) |
| 「两者都低」的诊断 | 这一类最值得查（通常是并行度不足或在等同步），但它的定义就是"两个利用率都低"，没有计数器连这个状态都识别不出来 |
| 量化的收益上界 | 只有访存受限的层才能从权重位宽减半里拿到接近线性的收益，详见[量化接入](quantization.md) |
| 预取是否有效 | 预取的效果就是缓存命中率，没有计数器只能看墙钟有没有变，而墙钟会被太多因素影响 |

### 一个不完整但可用的替代：解析法 roofline

在拿到计数器之前，对**访存量可以从 shape 解析出来**的算子，可以用这个办法做穷人的 roofline：

```
达成带宽 = 该 kernel 实际读写字节数 / duration_us
         其中读写字节数 = Σ(输入张量字节) + Σ(输出张量字节)
达成算力 = 该 kernel 的理论 FLOPs / duration_us
         GEMM: 2 × M × N × K;  逐元素: 元素数 × 每元素运算数

带宽利用率 = 达成带宽 / devices.models[].memory_bandwidth_gb_s
算力利用率 = 达成算力 / devices.models[].compute.<dtype>_tflops
```

适用范围：GEMM、逐元素、归一化、激活这类访存量确定的算子。
**不适用**：attention（实际访存量取决于实现是否 tiling，理论值会严重高估）、通信算子、带动态 shape 的算子。

前提是有 `input_shapes` 字段（即 `按 shape 聚类` 可用）。这一条让 `input_shapes` 的优先级高于直觉——它不只是用来分组，还是无计数器时唯一的受限类型近似。

## 需要你拍板的问题

| # | 问题 | 回答后能解锁什么 |
|---|---|---|
| 1 | 你的运行时能否在**单个 kernel 粒度**上给出开始与结束时间戳？还是只能给到整个 forward 这一级？ | 决定 T1 是否已经达成。不能的话，整组 4 个领域全部停在这里，第一件事是在运行时里补 kernel 级计时 |
| 2 | 芯片是否通过 PrivateUse1 接入 PyTorch，`torch.profiler` 能否拿到设备侧事件？ | 决定选项 A 是否成立。成立的话适配器工作量可能为零，直接复用现成的 chrome trace 适配器 |
| 3 | 硬件有没有性能计数器（PMU），驱动有没有暴露读取接口？ | 决定 T3 能不能建、选项 B/C 是否成立。为否则「访存受限判定」「roofline」「融合收益预估」永久不可用，相关 skill 一律降级为按耗时排序 |
| 4 | 读计数器是否需要 kernel 重放或串行化执行？ | 决定 counters 与 timeline 能否同一次采到。需要重放则必须走选项 C 的两次采集 + 离线合并 |
| 5 | 同一个算子在不同次执行中的 kernel 名是否完全稳定？名字里带不带 shape 或地址？ | 决定按名称聚合是否可靠，以及选项 C 的对齐键能不能用。名字不稳定时 Top-N 排序会失效 |
| 6 | profiler 产物是什么格式（chrome trace / CSV / 自有二进制），列名和时间单位是什么？ | 决定适配器怎么写。CSV 的话填 `profiler.kernel_table_columns` 即可复用现成适配器 |
| 7 | 采集时能否保留 step 标注，让设备 kernel 关联回主机侧的 step？ | 决定 T2 的 `按 step 切分` 能不能做，即能不能剔除首步、识别抖动 |
| 8 | 多卡采集时各 rank 的时间戳是否同源可比？ | 决定能不能画跨卡时间线、能不能把"通信慢"归因到具体的慢卡 |
| 9 | 计数器的"利用率"分母是什么——峰值规格，还是当前时钟下的理论值？ | 决定 `profiler.hardware_counters.memory_bound_threshold` 怎么标定。分母搞错会让受限判定系统性偏向某一边 |
| 10 | profiler 能否记录用户自定义标注（用来区分 prefill / decode）？ | 决定是否必须分两次采集。能标注的话建议给 schema 补一个可选 `phase` 字段 |

**回答顺序建议**：1 → 2 → 3。第 1 题为否则其余都不用问；第 2 题决定最便宜的路径通不通；第 3 题决定终局高度。
