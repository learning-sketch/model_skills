# 精度工具栈建设方案

> 三个训练精度领域——[不可复现](train-precision-determinism.md)、[NaN/Inf](train-precision-nonfinite.md)、[标杆不一致](train-precision-mismatch.md)——共用这一套底座。建议一次性建，不要三次重复造。

## 一句话结论

这三个领域缺的不是方法论，是**一个能按调用实例稳定命名、低开销常驻、支持跨运行自动比对的张量 dump 工具**；它可以完全建在 PyTorch 框架层，不依赖你的 runtime 或编译器改动，但"命名稳定性"和"零隐式同步"这两件事决定了它是能用还是只是能跑。

## 当前状态

**待建设。** CUDA 生态没有开源的对等物——NVIDIA 侧提供的是 `compute-sanitizer`（内存/竞态，不是数值）、Nsight（性能，不是数值）、`torch.autograd.detect_anomaly`（只管反向、只报位置不报数值）。框架级的 dump + compare 产品各家都是自建、不开源。所以这件事没有"接一个现成的"的选项，只有"建"和"不建"。

好消息是底座完全在 PyTorch 公开 API 的能力范围内：`nn.Module` hook、`TorchFunctionMode`、`TorchDispatchMode` 三层插桩点都是上游稳定接口。[硬件 profile](../../hardware-profiles/_TEMPLATE.yaml) 的 `precision_tools` 一节就是为登记这套工具的建设结果准备的。

## 一、这套工具到底要做什么

拆成四个能力。它们是递进的，但不是必须一次做完——阶段划分见第三节。

### 能力 1：分级采集

| 级别 | 采集单位 | 单 step 记录量级（7B 类模型） | 能回答 | 盲区 |
|------|---------|------------------------|--------|------|
| 模块级 | `nn.Module` 的 forward 输入/输出、backward 梯度、持有的 parameter 与 param.grad | 1e2 ~ 1e3 | 问题在第几层、在哪个子模块 | 看不到写在 `forward` 里的 functional 调用（`F.softmax`、`torch.matmul`） |
| API 级 | 一次 torch 函数调用 | 1e4 ~ 1e5 | 可疑模块内部是哪个算子 | 看不到 C++ 内部分解出的算子 |
| kernel 级 | 设备 kernel | 更大 | 算子内部哪一段 | 需要 runtime 配合，框架层做不到 |

两级之间必须能互相定位：**API 级的每条记录要带上它所属的 module 路径**。否则从模块级缩到 API 级时，你拿到的是一万条扁平记录，等于没缩。实现上是维护一个"当前 module 栈"——`forward_pre_hook` 压栈、`forward_hook` 弹栈，API 级插桩读栈顶。

### 能力 2：两种采集内容

**统计摘要**：每个张量只留几个标量。目标是能常驻开启、能覆盖全部 step 和全部调用。这是整套工具的主力模式，90% 的定位工作靠它完成。

**完整张量**：存原始数据。只能在已经定位到小范围之后定点开启。它的用途不是"找问题在哪"，而是"问题已经找到了，看看到底怎么回事"——取出两侧的输入输出做元素级分析，或者把输入原样导出构造最小复现用例交给算子团队。

还有第三种值得单列：**校验和**。它只回答"是否逐位相同"，用于确定性验证。为什么不能用数值摘要代替，见第四节决策 2。

### 能力 3：按调用实例对齐的比对

给两份 dump 产物，自动找出第一个超出阈值的调用实例。这是整套工具里 `print` 永远做不到、也是最值钱的能力。它要求每次调用有一个**跨运行稳定**的 ID，这是整个工具链的命门，见决策 3。

比对器的输出不应该是"所有不一致的地方"（那会是几千条，且下游的不一致都是上游的后果），而应该是**按执行顺序排序后的首个超阈值点，外加它上游若干个调用的摘要**。后半句是给人看的——首个超阈值点往往不是根因，根因在它上游的某个"还没超阈值但量级已经不对"的地方。

### 能力 4：异常扫描

与能力 3 不同，扫描**不需要标杆**，在单次运行内就能做：

- **非有限值扫描**：采集路径上顺带判 `isfinite`，命中则记录（可选中断）。
- **数值偏离扫描**：与历史比，不与绝对阈值比。某位置的 max 比它前 N 步大几个数量级、某层梯度范数为 0、某个激活整体塌缩成同一个值、某个权重在一步之内变化超过量级——这些都不需要参考实现就能判定可疑。
- **对称性检查**：DP 组内各 rank 在 all-reduce 之后的梯度应当一致，不一致本身就是结论。

## 二、为什么不能只用 print 或 detect_anomaly

这不是"手工麻烦一点"的区别，是几个数量级上的不可行。

**调用量。** 一个 7B 规模 transformer 的单个 step，aten 级算子调用在 1e4~1e5 量级（层数 × 每层算子数 × 前向反向 × 梯度累积）。`print` 一次只能看一个点，而且要改模型代码。

**要找的是"第一个"而不是"某一个"。** NaN 的传染性让它一旦出现下游全是 NaN；数值差异同理，第一个差异点之后的所有差异都是它的后果。有价值的只有首个。而"首个"这个定语意味着**必须全覆盖**——你没法通过撒几个点来确定第一个点在哪，只能确定它在某两个点之间，然后重跑。一个 step 要几分钟的时候，这个二分循环的成本不可接受。

**落盘体积。** 按 bf16、batch × seq = 4096 token、hidden 4096 估，单层每 token 的中间激活（qkv、attn 输出、MLP 中间态）合计数百 KB 量级，32 层下来单 step 的全部中间激活在几十 GB 级。全量存张量，一个 step 就把磁盘写满了。这是"统计摘要为主、完整张量为辅"这个设计不是优化而是**必要条件**的原因。

**多 rank。** 8 卡起步，每张卡有自己的调用序列。`print` 到 stdout 会交错且无法归属。更麻烦的是 TP 下同一个逻辑张量被切在不同 rank 上，单看一片没有意义。

**跨运行对齐。** 两次运行的"第 N 个 matmul"怎么对应？行号和全局序号都不是稳定 ID，因为下面这些东西都会让调用序列错位：激活重计算让同一个 module 的 forward 跑两次、MoE 路由在两次运行中选到不同专家、动态 shape 导致分支不同、算子融合在两个平台上把不同数量的算子合成一个。**没有稳定命名就没有自动比对**，没有自动比对这套工具就退化成一个昂贵的 print。

**`detect_anomaly` 的边界。** 它能告诉你反向图里哪个 backward function 产生了 NaN，并给出对应前向操作的 Python 调用栈——这确实有用。但它只管反向、不给数值、定位粒度是 autograd 节点（`AddmmBackward` 而不是"第 12 层的 down_proj"）、不做跨运行比对、开销大到无法常驻，而且在分布式下抛异常会打断集合通信，让其它 rank 卡在 all-reduce 超时上，真正的错误信息被淹没。详见 [NaN/Inf 文档](train-precision-nonfinite.md)。

## 三、分阶段建设路线

每个阶段都是**独立可交付**的——阶段 1 做完就能解决一部分真实问题，不需要等阶段 3。

### 阶段 1：基于 PyTorch hook 的统计摘要 dump

**做什么。** 遍历 `named_modules()` 挂 hook，对每个经过的张量在设备上算统计摘要，按 step 落盘成每 rank 一个的结构化文件。

**技术方案。** 前向用 `register_forward_pre_hook` / `register_forward_hook`；module 级梯度用 `register_full_backward_hook`；参数梯度用 `Tensor.register_post_accumulate_grad_hook`（PyTorch 2.1+，比 `register_hook` 更合适，因为它在梯度累加完成后触发，拿到的是最终值）。module 路径（`model.layers.3.mlp.down_proj`）直接作为命名的主干。落盘用 jsonl——可追加、崩溃了前半段仍可读，比对器入口处再转 DataFrame。

**解锁。** 「问题在第几层」这一类问题全部可答：非有限值出现在哪个模块、各层激活与梯度的幅度随 step 的演化曲线、单次运行内的异常扫描、DP 组内梯度一致性检查。[NaN/Inf 文档](train-precision-nonfinite.md)里的阶段划分法在这一阶段就完全可用。

**改动点。** 一个独立 Python 包 + 训练脚本加几行启用。不改模型代码，不改 runtime，不改编译器，不改训练框架。这是整套工具里侵入性最低的一步，也是为什么建议从这里开始。

**坑。**

- **`.item()` 是头号杀手。** 一个 step 上千个 hook，每个 hook 调一次 `.item()`/`.cpu()`/`float(t)` 就是上千次强制同步，训练会慢几十倍，而且执行时序被彻底改变（见决策 6）。正确做法：统计量全部以标量张量形式攒在设备 buffer 里，step 末尾一次性 D2H。
- **低精度必须先 upcast。** bf16 直接 `sum` 一个 1e8 元素张量，累加误差会让 mean 毫无意义；fp16 更会直接溢出成 inf 造成假阳性。统计量一律先转 fp32 再算。
- **`register_full_backward_hook` 有使用前提。** 它只对 module 的直接输入输出张量生效，module 内部有原地操作时会报错或行为异常，多输出/输出非张量的 module 也要特判。需要准备一条降级路径（退回到对输出张量挂 `Tensor.register_hook`）。
- **激活重计算会让前向触发两次。** `torch.utils.checkpoint` 包住的 module，一个 step 内 forward 跑两遍。必须能区分这两次，否则记录会互相覆盖。
- **module hook 有结构性盲区。** 写在 `forward` 里的 `F.softmax`、`torch.matmul`、`+` 都不是 module，看不到。这是阶段 2 引入 API 级的理由，不是阶段 1 的 bug。
- 分布式下非 rank 0 的进程也要写，文件名必须带 rank。

### 阶段 2：调用实例对齐与自动比对

**做什么。** 给每次调用一个跨运行稳定的 ID；写一个比对器把两份 dump 配对，算差异指标，输出按执行顺序排序的首个超阈值点。

**技术方案。** 命名方案见决策 3。API 级插桩引入 `TorchFunctionMode`（用 `with` 包住训练循环即可，不改模型代码），并在记录里带上从 module 栈取到的所属路径。比对器按 ID 做 outer join，对摘要记录比相对差，对完整张量记录算相对误差、最大绝对误差、余弦相似度。

**容错是这一阶段的硬要求。** 两边的 ID 集合不完全相等是常态而非异常——跨平台时一边的融合算子对应另一边三个算子，ID 根本对不上。比对器必须能正常输出并**显式列出"仅在单侧出现"的调用**，而不是崩溃或静默丢弃。静默丢弃最危险：你会以为比对通过了。

**解锁。** [标杆不一致](train-precision-mismatch.md)的完整诊断流程；[不可复现](train-precision-determinism.md)的首个差异点定位（同一硬件两次运行互为标杆）。这两个领域从"只能看 loss 曲线"跃升到"能指到具体调用"。

**改动点。** 主体是工具侧（命名模块 + 比对器）。采集侧需要加 module 栈的上下文传播。如果要 API 级，需要引入 `TorchFunctionMode`，它会接管所有 torch 函数调用，对性能和与其它 mode/subclass 的交互要实测。

**风险。** 命名稳定性是这一阶段的全部成败。重计算、动态控制流、动态 shape、编译期融合都会破坏序号对齐。更麻烦的是失败方式是**静默的**——ID 错位时比对器照样产出结果，只是结果全错。必须有一个自检：同一份 dump 和自己比对，结果必须是零差异；两次确定性运行比对，结果也必须是零差异。这两条自检不过，比对器的任何输出都不可信。

### 阶段 3：定向张量 dump 与根因定位

**做什么。** 在阶段 2 定位出的可疑调用上开完整张量 dump，离线做元素级分析。

**技术方案。** 范围过滤（step 列表 + module 路径前缀 + 调用 ID 白名单）决定哪些调用被命中。命中后 D2H 拷贝**必须在 hook 里立即发起**——很多算子会原地改写输入，晚一步拿到的就是被改过的值；但写盘可以异步，走 pinned memory 中转 + 独立 copy stream + 后台写盘线程。存储上每个张量一个独立文件（npy 或 safetensors）配一个索引，不要用一个大 `torch.save`——根因分析往往只要取其中两三个张量，整体加载不可接受。

**元信息和数值一样重要。** 存 shape、dtype、stride、device、是否连续。不要偷偷 upcast 成 fp32 存——那会掩盖 dtype 本身就是问题的情况。stride 和连续性尤其关键：张量布局转换是自研芯片的高频真因，而它在数值上的表现可能只是"某些 shape 下误差突然变大"。

**另外值得在这一阶段做的是触发式环形缓冲**：平时只采摘要，内存里保留最近 K 个调用的完整张量，一旦扫描到非有限值就把缓冲整个落盘。这解决了偶发事故无法预知在哪一步的问题，代价是常驻一块可观的内存。

**解锁。** 从"哪个调用出问题"进到"为什么出问题"。累加顺序、中间精度、布局转换、通信规约这四类真因在误差的空间分布上有不同指纹（见[标杆不一致](train-precision-mismatch.md)的真因表），只有拿到完整张量才能读出这些指纹。同时能把可疑调用的输入原样导出，构造脱离训练框架的最小复现用例。

**改动点。** 需要新建异步拷贝与落盘子系统，要和你的 runtime 的 stream/event 语义打交道。这是全套里工程量最大、最容易出细微 bug 的部分。

**坑。**

- 观察者效应在这一阶段最严重（决策 6）。
- 显存：pinned buffer、在途张量、后台队列都占内存。本来就接近 OOM 的训练一开张量 dump 就 OOM，或者 allocator 分配模式变了触发不同的碎片行为。
- **必须有背压。** 落盘速度跟不上产生速度时，要阻塞或丢弃**并显式记录**，绝不能静默丢数据——静默丢数据会让你以为"这个位置没问题"。

## 四、关键技术决策

### 决策 1：插桩点选在哪一层

| 方案 | 覆盖 | 侵入性 | 命名稳定性 | 主要限制 |
|------|------|--------|-----------|---------|
| `nn.Module` hook | 只到 module 边界 | 最低，不改模型代码 | **高**，module 路径由结构决定 | 看不到 functional 调用；原地操作下 `full_backward_hook` 受限 |
| `TorchFunctionMode` | Python 层 torch API 全覆盖 | 中，`with` 包住训练循环 | 中 | 看不到 C++ 内部分解出的算子；被 `torch.compile` 捕获的图不触发 |
| `TorchDispatchMode` | aten 层全覆盖，含反向 | 中 | **低** | 开销最大；与 autograd/tensor subclass 交互复杂；会看到大量无关的琐碎算子 |

**建议：三者分层而非择一。** 阶段 1 只用 module hook，阶段 2 加 `TorchFunctionMode`，`TorchDispatchMode` 留作阶段 3 的可选深挖。

反直觉的地方在于：覆盖最全的那个（dispatch）恰恰最不适合做比对的主力。因为它贴近实现，两个平台、两个框架版本之间的 aten 调用序列最容易不一致，而比对需要的是**稳定**而不是**全面**。全面是定位到范围之后才需要的。

这取决于你的栈怎么实现：如果后端走 PrivateUse1 且大量算子注册在自定义 dispatch key 上，`TorchDispatchMode` 看到什么需要实测；如果训练主路径默认开 `torch.compile`，Dynamo 会把整段图捕获走，上面三种 Python 层插桩**全部失效**，必须准备一个"诊断模式强制 eager"的开关，并接受"eager 下不复现"本身是一条信息。

### 决策 2：摘要存什么

| 摘要量 | 能答 | 答不了 |
|--------|------|--------|
| max / min | 非有限值、量级爆炸或塌缩、激活饱和 | 分布内部的差异 |
| mean | 整体偏移、是否全零 | 正负抵消掉的误差 |
| L2 norm | 整体幅度；梯度消失/爆炸的标准指标 | 稀疏的少数异常元素（被平均掉） |
| 非有限值计数 | 有多少个 NaN/Inf，而不只是有没有 | 在哪些位置 |
| 零元素占比 | 死神经元、mask 是否生效、通信缓冲是否真的被写入 | — |
| 校验和 / 逐位哈希 | **是否逐位相同**，确定性验证的最强判据 | 不同的时候差多少，完全无信息 |

**校验和与数值摘要回答的是不同类型的问题，不能互相替代。** 校验和只有两种答案，适合确定性验证——同硬件同配置两次运行，逐位相同才算真确定，任何数值摘要都给不出这个强度的结论（摘要相同不代表张量相同）。反过来，跨平台比对时校验和的答案永远是"不同"，信息量为零，必须用连续的数值指标。所以这是两个独立的开关，不是一个选项的两种取值。

**建议默认集合**：max / min / mean / L2norm / 非有限值计数 / 元素数。这几个都能在设备上算、都是单次 reduce、合起来每个张量几十字节。校验和作为确定性场景的独立开关。

### 决策 3：调用实例怎么命名才跨运行稳定

候选方案：

| 方案 | 稳定性 | 失效条件 |
|------|--------|---------|
| 全局调用序号（`op_1234`） | 最差 | 任何一处分支差异让后面全部错位。**不要用作主键** |
| module 路径 + 同路径调用计数 | 好 | 路径由模型结构决定，只在模型结构改变时变 |
| Python 调用栈哈希 | 对同一份代码很好，跨代码改动即失效 | 不适合长期基线 |
| FX / 编译图上的节点名 | 最好 | 只在图模式下存在 |

**建议主键**：`{rank}/{step}/{module_path}/{同键序号}/{phase}/{slot}`。API 级在 `module_path` 后追加 `{api_name}/{module 内同名序号}`。把 rank 和 step 显式放进主键，因为比对时经常要做"同 rank 跨运行"和"同 step 跨 rank"两种切片。

必须单独处理的四种情况：

- **激活重计算**：同一 module 一个 step 内 forward 两次，序号变成 0 和 1。要么在记录里标 `recompute` 标志，要么接受序号区分但保证两次运行的触发次数一致。
- **动态控制流**：MoE 的 top-k 路由在两次运行中可能选到不同专家，专家 module 的调用序号天然对不齐。这时路径里必须包含**专家 ID** 而不是依赖序号。
- **梯度累积**：micro-batch 之间 module 路径和序号完全相同，必须把 micro-step 并入主键。
- **权重共享**：同一个 module 对象被调用多次（如 tied embedding），靠同键序号区分，但要确认两次运行的调用顺序一致。

### 决策 4：落盘格式与开销控制

摘要用 jsonl（可追加、崩溃可读、比对器入口转 DataFrame），张量用"一张量一文件 + 索引"。

开销控制有四个旋钮，应当都做出来而不是只做一个：

1. **采样**：支持"前 N 步全采 + 之后按步长采 + 指定 step 列表"。精度问题常在特定 step 出现，纯等间隔采样会错过。
2. **范围过滤**：module 路径前缀白/黑名单。大模型的 N 个 transformer layer 结构相同，常规情况下只采第 0、N/2、N-1 层就够定位。
3. **异步**：摘要攒设备 buffer、step 末批量 D2H；张量走独立 copy stream + pinned buffer + 后台写盘。
4. **内容降级**：默认只摘要，完整张量靠白名单开。

有一条应当当作硬性规则：**采集路径上不允许出现隐式同步**。`.item()`、`.cpu()`、`.tolist()`、`float(tensor)`、`print(tensor)`、任何 Python 层的条件判断依赖张量值——全是同步点。这条规则的违反不仅是性能问题，更会改变执行时序，见下一条。

### 决策 5：多 rank 怎么合并

三种关系要分开处理，混在一起会得到无意义的结果：

| 并行方式 | 同一逻辑量在各 rank 上的关系 | 比对策略 |
|---------|--------------------------|---------|
| DP / FSDP | 激活各不相同（输入不同）；梯度在 all-reduce **之后**应当一致 | "all-reduce 后梯度是否跨 rank 一致"本身是一条强判据，不一致说明通信有问题 |
| TP | 同一逻辑张量被切成几片分散在各 rank | 与单卡标杆比对前必须按切分维度拼回。需要 dump 记录里带切分元信息（哪个维度、第几片），框架不会自动提供 |
| PP | 各 rank 持有不同的层 | 必须按"全局层号"而非"本地 module 路径"对齐，取决于框架是否重编号 |

**建议：阶段 1 和 2 不做跨 rank 自动合并。** 每 rank 独立落盘、独立比对，工具只保证 rank 在主键里。TP 拼接放到阶段 3，且需要并行框架提供切分元信息的约定。早期就做自动合并，会在并行配置稍一变化时全盘失效，且失效方式是静默的。

### 决策 6：观察者效应

这是最容易被忽略、又最伤的问题。dump 从三个方向改变被测系统：

- **时序**：插入 D2H 拷贝和同步点，改变 kernel 的下发与执行重叠关系。竞态类 bug（算子内部 race、通信与计算 race）对时序极度敏感，一开 dump 就不复现。
- **显存**：pinned buffer、在途张量、后台队列占额外内存；allocator 的分配模式改变，触发不同的碎片行为，也会改变"读到未初始化内存时读到什么"。
- **执行路径**：hook 里持有张量引用会延长其生命周期，可能阻止某些原地优化；dispatch 模式还可能改变算子分解方式。

应对手段，按优先级：

1. **先用最接近零干扰的配置跑一轮**：纯设备端统计量 + step 末批量 D2H + 不落张量。如果问题在这个配置下仍复现，后面都好办。
2. **如果一开 dump 问题就消失，这个事实本身是结论，不是失败。** 它强烈指向竞态或未初始化内存读取。此时应当立刻转去做 sanitizer 检查和通信同步点审计，而不是继续加大 dump 力度——加大只会让它更不复现。
3. **分层收敛**：先最轻配置定位到小范围，再在小范围上加重。不要一上来就全量张量 dump。
4. **记录配置指纹**：每份产物里存采集配置、框架版本、并行配置、相关环境变量。两份 dump 的配置不同时，比对结论要打折，工具应当主动提示。
5. **提供"只统计不落盘"模式**：摘要攒在内存里，只在触发条件命中时写出。这是开销最低的常驻配置。

## 五、验收标准

每一条都应当可机器检验，建议直接做成工具自己的回归测试。

**阶段 1**

- 开启后端到端 step 时间的增加**可测量且稳定**（建议以 10% 为目标；具体数字取决于你的 D2H 带宽和 hook 数量，重要的是有基线、有回归监控，而不是某个特定数值）
- 不改模型代码即可对任意 `nn.Module` 子树启停
- 单 step 摘要产物在 MB 级而非 GB 级
- 人为在某一层注入 NaN，产物标出的是**该层**而不是它下游的层
- 多 rank 下各 rank 产物独立完整，不互相覆盖
- **开启采集不改变 loss 的数值**（同一确定性配置下逐位相同）——这是"采集无副作用"的最强证明，也是最容易被忽略的一条

**阶段 2**

- 同一份 dump 与自己比对：零差异
- 同一硬件、确定性配置下两次运行比对：零差异
- 人为改一行代码（例如某个 norm 的 eps 从 1e-5 改成 1e-6），比对器报告的首个差异点就是那一层，且不被下游的大量差异淹没
- 两侧 ID 集合不完全相同时正常输出，并显式列出"仅单侧出现"的调用
- 比对一个 32 层模型的全量摘要产物，耗时在分钟级

**阶段 3**

- 能从比对结果中选中一个调用 ID，一条命令取出该调用在两侧的完整输入输出
- 取出的张量 shape/dtype/stride 与运行时一致；用这些输入重放该算子（同硬件）能复现当时的输出
- 范围过滤生效：只采 1 个 module 时，产物体积与耗时相比全量有数量级差距
- 显存增量可预测且有上限：队列满时阻塞或显式报告丢弃，绝不 OOM、绝不静默丢数据

## 六、需要你拍板的问题

| # | 问题 | 回答后能解锁 |
|---|------|------------|
| 1 | 你的栈现在有任何形式的张量 dump 能力吗（哪怕只是 runtime 层的裸内存 dump）？ | 决定是从零建还是在已有基础上加框架层，直接影响阶段 1 的起点 |
| 2 | 训练主路径是 eager，还是 `torch.compile` / 图捕获为主？ | 决定插桩点选型；图模式下三种 Python hook 全部失效，必须先建"诊断模式强制 eager"的开关 |
| 3 | 用的训练框架是什么（Megatron-LM / torchtitan / 自研）？ | 决定 TP/PP 切分元信息从哪里取、重计算上下文怎么识别、是否已有可复用的 RNG 与 nan 检查设施 |
| 4 | 有没有可信的标杆平台（CPU fp32？另一个硬件？）？ | 决定[标杆不一致](train-precision-mismatch.md)这个领域是否成立；没有标杆时比对能力只能用于自比对 |
| 5 | `torch.use_deterministic_algorithms(True)` 在你的后端上的实际行为是什么（真生效 / 静默忽略 / 遇到无确定性实现时抛错）？ | 决定[不可复现](train-precision-determinism.md)的门禁能否成立，以及校验和模式有没有意义 |
| 6 | 最先要解决的是哪一类问题（不可复现 / NaN / 对不齐标杆）？ | 决定阶段 1 的默认采集配置往哪边偏——确定性场景偏校验和，NaN 场景偏非有限值计数，标杆场景偏数值摘要 |
| 7 | 单次 dump 产物可接受的存储上限和落盘路径（本地盘？共享存储？）？ | 决定采样与范围过滤的默认策略，以及异步落盘要不要做背压 |
| 8 | 精度调试时能否独占整机（不与其它作业共享）？ | 决定能否接受观察者效应较大的配置；共享环境下时序本身就不稳定，竞态类结论不可信 |
