# 推理精度问题诊断

> 组 1。等级 **C**（需要先建设一个专门的底层能力）。范围集中在 KV cache 与 attention 相关的精度问题。

## 一句话结论

**推理精度问题的排查方法论是完全通用的，而且其中最省时间的两步——用 prefill/decode 做二分、用 decode 第 1 步与第 N 步做二分——不需要任何工具，现在就能用；真正卡住的是 attention 算子的参数契约，这是最容易出错、也最无法通用化的部分。**

## 当前状态

| 现在能做 | 还差什么 |
|---|---|
| 本文「排查方法论」与「逐层对比」两节与芯片无关，立刻可执行 | 逐层对比需要一个能按调用实例对齐的 dump 工具。`hardware-profiles/` 的 `precision_tools` 一节全是 `null` |
| 「典型根因清单」八类全部是通用根因，可以直接当检查表用 | 其中三类（地址映射、mask 组合、脏数据）的确认方法依赖算子契约，契约未知时只能靠实验试探 |
| 贪心解码下的逐 token 比对现在就能做，是最严也最便宜的判据 | 没有已知正确的参考实现时，所有对比式方法全部不成立 |

**与组 2 的关系**：训练侧的三个精度领域共用一套 dump 与比对底座（见 [`_precision-toolchain.md`](_precision-toolchain.md)）。推理侧的逐层对比可以复用同一套底座，但**推理独有的对齐维度是"第几个 decode step"**，训练侧没有这个概念，工具要支持它。

## 排查方法论

### 前提：没有参考就没有诊断

精度问题的全部方法都是对比式的。开始之前必须先有一个**已知正确的参考输出**，按可信度排序：

1. 同一份权重在 CPU fp32 上的输出（最可信，也最慢，只能跑很短的用例）
2. 成熟框架在另一种硬件上的 eager 输出
3. 同一张卡上的朴素实现（不用分页、不用融合算子、不用图模式的那条路径）

第 3 种最实用：它把"算子实现错了"与"接入方式错了"分开，而后者占实际问题的绝大多数。[KV cache 接入](../../skills/model-infer-kvcache/SKILL.md)的三级降级路径（朴素 → 索引层 → 真算子）正是为此设计的，每一级的参考输出就是上一级。

**纪律：参考输出必须在问题出现之前就存起来。** 出了问题再去补一个参考，那时已经分不清参考本身对不对。

### 单变量

一次只改一个东西，改完立刻比对。听起来是废话，但精度问题特别容易诱使人"一起改几个看看"——因为单改一个往往没变化。没变化本身就是信息（说明这个因素无关），比"改了五个，好了，不知道哪个起作用"有价值得多。

同时要固定住：随机种子、采样策略（优先直接用贪心解码，彻底消除随机性）、batch 组成、输入长度、并发度。其中**batch 组成和并发度最容易被忽略**，而它们恰好是第 4、5 类根因的触发条件。

### 二分一：用 prefill / decode 切

这是收益最高的一步，因为它把根因空间砍掉一多半，而且不需要任何工具。

做法：
- **prefill-only**：把参考输出的完整 token 序列一次性喂进去做 prefill（teacher forcing），比较所有位置的 logits。这条路径不碰 decode 的任何逻辑
- **decode-only**：用同一个 prompt 走正常生成，逐 token 比对

| 现象 | 指向 | 排查顺序 |
|---|---|---|
| prefill 对、decode 错 | **KV cache 的读写路径**——地址映射、序列长度、位置编码偏移、decode 分支的 mask | 根因 1 → 2 → 7 |
| 两者都错 | **与 KV cache 无关**——算子本身、权重加载、dtype、张量布局 | 根因 8 → 6 → 卡在哪一节的契约项 |
| prefill 错、decode 对 | 罕见但指向极明确：**变长/padding 布局或 mask 构造** | 根因 3 → 5 |

两者都错时，先做根因 8（权重加载）的检查——它最便宜，而且一旦命中，后面所有排查都白做。

### 二分二：用 decode 第 1 步 / 第 N 步切

prefill 对、decode 错之后，继续二分：

| 现象 | 指向 |
|---|---|
| 第 1 步就错 | 与历史累积无关，是 decode 路径本身：单 token 的 attention 调用、本步 KV 的写入位置、传给算子的序列长度 |
| 第 1 步对、第 N 步错 | 与累积有关。**N 的具体取值本身就是最强的线索** |

**N 是多少，直接指向不同的根因**：

- N 落在 `block_size` 的整数倍附近 → 跨块边界。块表追加逻辑或新块的分配/初始化
- N 等于某个预计算表的长度（RoPE 的 cos/sin 表、mask 缓存） → 表越界或回绕
- N 等于滑动窗口大小 → 窗口滑动时的块回收或 mask 下界
- N 等于某个 2 的幂（256 / 32768） → 整数位宽或索引类型溢出
- 没有特定的 N，误差随步数平滑增长 → 这不是 bug，是正常的数值累积，去看误差量级而不是去找错

**这一步的价值在于它几乎不花成本**：只要记录"从第几步开始偏离"，就能把排查范围从八类根因缩到一两类。

## 逐层对比

二分定位到阶段之后，用逐层对比找出**第一个出错的层**。注意是第一个——之后的层全都会错，看它们没有意义。

### 检查点怎么放

第一轮只放最小集：`embedding 输出` → `每层的输出` → `最终 norm 输出` → `logits`。定位到具体某一层之后，再在那一层内部加密：`q/k/v 投影输出` → `RoPE 之后` → `attention 算子输出` → `attention 输出投影` → `残差相加后` → `MLP 各子步`。

一上来就全放会产生两个问题：dump 体积爆炸，以及被"每一层都有微小差异"淹没而找不到真正的台阶。

**对齐是这件事最容易错的一环。** 检查点必须按 `(step, layer_index, 同一模块在本步内的调用序号)` 三元组对齐，不能只按模块名。同一个模块在一步内被多次调用的情况比想象中常见：分块 prefill 把一次前向切成了多块、权重共享的层、投机解码的草稿模型。只按名字对齐会把第 2 次调用的结果和参考的第 1 次调用比，得出一堆假阳性。

其余纪律：

- 采集方式用 forward hook 可以覆盖模块边界；要抓模块内部（比如 RoPE 之后）必须在代码里手工插桩，没有别的办法
- **只在第一个出错的 token 上做层扫描**。全量 dump 的体积是 `层数 × 张量字节 × token 数`，很快到 TB 级
- 分级 dump：先只存统计量（`min` / `max` / `mean` / `std` / NaN 计数 / Inf 计数），体积极小且足以发现爆点；统计量异常的那一层再存整张张量
- 两侧用同样的 dtype 保存，建议统一提到 fp32。否则比较的是两次不同的截断结果

### 误差度量选哪个

| 度量 | 定义 | 擅长发现 | 盲区 |
|---|---|---|---|
| 最大绝对误差 | `max\|a−b\|` | **单点爆点**：某个位置读到了错的 KV、索引越界、脏数据 | 随张量量级放大，不同层之间不可比 |
| 最大相对误差 | `max\|a−b\| / (\|b\|+ε)` | **整体量级问题**：缩放因子错、dtype 截断 | 接近 0 的元素制造大量假阳性，必须配合 `\|b\| > 阈值` 过滤 |
| 余弦相似度 | `⟨a,b⟩ / (‖a‖‖b‖)` | **结构性错误**：张量布局错、head 顺序错、batch 间串数据 | 对整体缩放**完全不敏感**——scale 错 100 倍，余弦仍是 1.0 |
| 相对 L2 | `‖a−b‖₂ / ‖b‖₂` | 整体漂移程度，最适合画逐层曲线 | 掩盖单点爆点：十万个元素里错一个基本看不出来 |

**必须至少同时看最大绝对误差、余弦相似度、相对 L2 三个。** 只看一个一定会漏掉一整类问题。两两组合的判读：

| 最大绝对误差 | 余弦相似度 | 判读 |
|---|---|---|
| 大 | ≈ 1 | 整体缩放或个别位置爆点。查缩放因子、查单点 |
| 大 | 明显 < 1 | **结构性错误**。布局、顺序、串数据。不要去调阈值，去查契约 |
| 小 | 明显 < 1 | 张量本身量级就小，相对而言错得很厉害。**不要因为绝对值小就放过** |
| 小 | ≈ 1 | 这一层没问题，继续往后 |

### 阈值：判据是"跳变"不是绝对值

bf16 的尾数是 8 位，机器精度约 `2⁻⁸ ≈ 3.9e-3`；fp16 的尾数是 11 位，约 `2⁻¹¹ ≈ 4.9e-4`。由此得到的参考范围：

| 场景 | bf16 | fp16 | 说明 |
|---|---|---|---|
| 单算子对拍（同输入同权重） | 相对误差 `1e-2` 内正常 | `1e-3` 内正常 | 超出说明算子实现有实质差异，不是舍入 |
| 整模型逐层累积到最后一层 | 相对 L2 `1e-2` 量级仍可能正常 | `1e-3` 量级 | 层数越多累积越大，没有一个放之四海的数 |
| 任意一层的余弦相似度 | `< 0.99` 值得查，`< 0.9` 基本是结构性错误 | 同 | 余弦对累积误差不敏感，所以阈值可以卡得很死 |
| 贪心解码的 token id | **必须完全一致** | 同 | 最严也最便宜的判据，优先用它 |

**真正可靠的判据是误差增长曲线有没有台阶。** 把相对 L2 按层号画出来，正常形态是缓慢单调增长；某一层出现一个跳变（比如从 `2e-3` 跳到 `5e-2`），那一层就是首个差异点。绝对阈值只用来兜底——因为"多少算正常"强烈依赖模型深度、dtype、输入分布，而台阶是自明的。

token id 比对有一个要注意的地方：当 top-1 与 top-2 的 logit 差距很小时，正常的数值噪声也会翻转结果。所以 token id 不一致时，**先看翻转位置的 top-2 margin**——margin 小于该 dtype 的噪声量级就不算证据，应改看 top-5 集合是否一致。

## 典型根因清单

这八类覆盖了 KV cache 与 attention 接入阶段的绝大多数精度问题。全部与具体芯片无关。

**1. 分页 KV 的地址映射写错**
症状：输出语法通顺但语义错乱，**不报错**；越界严重时才会触发非法内存访问。
为什么容易错：扁平化的 `slot = block_id × block_size + offset` 只在"块内按 token 连续"的布局下成立；块内按头优先存放时必须拆成两级索引。两种布局在业界都有实现，没有默认。
怎么确认：随机抽若干 `(序列下标, 位置)`，按地址公式从 cache 读回，与写入时的 k/v 向量比对。

**2. 序列长度生命周期管理错误**
症状：典型的 off-by-one——输出整体像"少看了一个 token"或"多看了一个"，第 1 个 decode step 就错。
为什么容易错：`seq_len` 是否包含当前 token，取决于实现是"先写 cache 再算 attention"还是反过来；抢占换出后恢复的长度、分块 prefill 的已缓存长度都是额外的出错点。
怎么确认：每步打印 `(query_len, context_len, seq_len)` 与手算期望值比对；在 attention 入口断言 `seq_len` 等于该序列已写入的 slot 数。

**3. mask 与稀疏模式组合错**
症状：长序列才错，或 prefill 错而 decode 对。
为什么容易错：`q_len ≠ kv_len` 时 causal mask 必须**右下对齐**（query 的最后一个位置对齐 key 的最后一个位置），分块 prefill 和前缀复用都会进入这个分支；算子内置 causal 与外部传入的 additive mask 可能重复施加（更严，看不到该看的）或互相抵消（看到了未来）；滑动窗口与 causal 叠加时下界算错；整行全被屏蔽时 softmax 的分母为 0，在低精度下直接产生 NaN。
怎么确认：构造一个极小用例（4 个头、8 个 token），把 attention 权重矩阵整个打出来直接看形状。这比任何间接推断都快。

**4. 多轮对话残留脏数据**
症状：**偶发**、与并发历史相关、单独重跑复现不了。这是八类里最难查的。
为什么容易错：块回收后通常不清零（清零的带宽开销在高吞吐下不可忽略），如果算子按**整块**读取 KV，就会读到上一个请求留下的数据；引用计数提前归零也会造成同样现象。
怎么确认：A/B/A 测试——跑 prompt A 记录输出，跑 prompt B，再跑 A，两次 A 的 token 序列必须完全一致。确诊手段是临时改成"回收时清零"，问题消失即坐实。

**5. batch 间串数据**
症状：单条跑对、组 batch 跑错，且出错位置与序列在 batch 内的位置相关。
为什么容易错：变长布局下的累积长度数组算错一位、padding 位置参与了 softmax、块表行错位、某个张量在 batch 维上被广播而不是索引。
怎么确认：交错批测试——A 与 B 同批跑，各自结果必须与单独跑时完全一致；再把 batch 内顺序打乱重跑，结果应当跟着一致地换位，不跟着换就是索引用错了。

**6. dtype 隐式提升 / 截断**
症状：结构正确但误差偏大（余弦 ≈ 1、相对误差超预期）；或 fp16 下长序列出现 Inf/NaN。
为什么容易错：mask 用 fp32 而 score 是 bf16，相加会把整段提升（慢但不错）或被截断（错）；fp16 的最大值是 65504，attention score 或中间激活超出就溢出；累加器用 fp16 还是 fp32 对长序列影响很大；缩放因子在类型转换之前还是之后施加，结果不同。
怎么确认：逐检查点打印 dtype；把可疑的一段临时整体提到 fp32 重跑，误差消失即确诊。

**7. RoPE 位置编码偏移**
症状：前几个 token 对、之后逐渐发散；或只有长 prompt 才错。
为什么容易错：decode 时的 position 必须是已缓存长度而不是 0；分块 prefill 时 position 要加上已缓存长度；**interleaved 排布与 half-split 排布互不兼容**（同一张 cos/sin 表，两种配对方式算出来完全不同，且都不会报错）；预计算表长度不够导致越界或回绕；长上下文缩放的配置与权重训练时不一致。
怎么确认：固定一个位置单独调 RoPE 与参考实现比对；特别地，比对 `position=0` 与 `position=1` 的输出差异是否符合旋转角度的预期。

**8. 权重未完全加载（尤其 MoE 专家）**
症状：稠密模型下整体乱码；**MoE 下表现为大部分 token 正常、少数 token 胡言乱语**——那些 token 恰好被路由到了没加载的专家。
为什么容易错：专家权重的名字带编号，按名称模式加载时正则容易漏掉一部分；gate 与 up 合并存储时切分位置错；tied embedding 没处理；量化的 scale 张量不在常规参数列表里，极易整批漏掉。
怎么确认：加载完成后统计**被显式赋值的参数量占模型总参数量的比例，必须是 100%**；再对每个参数打印 `(mean, std, abs_max, 零元素比例)`，仍是初始化分布或全零的一眼可见。MoE 要按专家逐个统计，不能只看总量。

**这一项应当作为任何精度排查的第 0 步**，因为它最便宜、命中率不低、而且一旦命中会让后面所有排查作废。

## 卡在哪：attention 算子的参数契约

上面八类根因里，第 1、3、5 类的确认方法全都依赖一件事——**知道你的 attention 算子到底约定了什么**。这是整个领域最容易出错、也最无法通用化的部分，因为下表每一项在业界都有至少两种并存的约定，没有事实标准；而且**猜错的表现几乎总是静默输出错误结果，不是报错**。

| 契约项 | 为什么必须问清 | 猜错的表现 |
|---|---|---|
| KV cache 的维度顺序 | 决定地址公式能不能扁平化 | 输出乱码，不报错 |
| K 与 V 是否同一种布局 | 部分实现里两者不同 | 只有 V 相关的部分错，更难定位 |
| mask 是 bool 还是 additive；`True` 表示保留还是屏蔽 | 两种约定都常见 | 语义完全反过来，变成只看未来 |
| 是否内置 causal；`q_len ≠ kv_len` 时往哪边对齐 | 决定调用方要不要再给一个 mask | 重复施加（过严）或互相抵消（看到未来） |
| 缩放因子在哪施加——算子内部乘 `1/√head_dim`，还是调用方预先乘到 q 上 | 这是最常见的重复/遗漏点 | 重复乘 → 分布过平，输出"过于随机"；漏乘 → 过尖，输出"过于确定" |
| 是否内置 softmax 的数值稳定化（减最大值） | 决定长序列会不会溢出 | fp16 下长序列出 NaN |
| 内部累加用什么 dtype | 决定误差的正常量级 | 误差大于预期但结构正确，容易被误判成"实现错了" |
| 是否按**整块**读取 KV（会读到 `seq_len` 之后的槽位） | 直接决定脏数据必须不必清零 | 根因 4 的偶发错误，极难复现 |
| padding / 无效位置的忽略值约定 | 决定 slot 映射里填什么 | 写坏了别的序列的 cache，错误跨请求传播 |
| `head_dim` / `block_size` / KV dtype 的取值约束 | — | 报错，或静默走了一条降级路径 |

这张表与 [`model-infer-kvcache`](../../skills/model-infer-kvcache/SKILL.md) 的「profile 未覆盖、必须向用户确认的信息」是同一份契约的两面：那边关心"怎么接进去"，这边关心"接错了怎么查出来"。**建议把它整理成一份随算子一起维护的文档**，口头约定一定会丢。

## 需要你拍板的问题

| # | 问题 | 回答后能解锁什么 |
|---|---|---|
| 1 | 有没有一个已知正确的参考实现可以对拍（CPU fp32 / 另一种硬件 / 本卡的朴素路径）？ | 决定全部对比式方法能否成立。没有参考时只能做自洽性检查，诊断能力下降一个数量级 |
| 2 | 能不能用 PyTorch 的 forward hook 逐层取出张量（对应 `precision_tools.pytorch_hooks_usable`）？ | 决定逐层对比要不要自建。能用 hook 的话最小集检查点可以零成本铺开 |
| 3 | 你的 attention 算子有没有一份参数契约文档，覆盖「卡在哪」那张表的十项？ | 决定根因 1 / 3 / 5 能不能快速确认，还是只能靠实验试探。这是本领域最大的单点阻塞 |
| 4 | 分页 attention 算子是否按整块读取 KV？ | 决定块回收时必须不必清零，直接决定根因 4 能不能被排除 |
| 5 | KV cache 的块内布局是 token 连续还是头优先？ | 决定地址公式能否扁平化，也就是根因 1 的检查怎么写 |
| 6 | RoPE 用的是 interleaved 还是 half-split 排布，cos/sin 表预计算到多长？ | 决定根因 7 的两个最常见分支能不能一次排除 |
| 7 | 权重加载路径有没有"赋值覆盖率"统计？MoE 的专家权重是怎么命名和切分的？ | 决定根因 8 能不能在三分钟内排除。建议无论如何都补上这个统计 |
| 8 | 要不要和组 2 的训练精度工具共用一套 dump/比对底座？ | 决定建设范围。共用的话要额外支持"第几个 decode step"这个推理独有的对齐维度 |

**回答顺序建议**：1 → 3。第 1 题为否，方法论全部降级；第 3 题是本领域真正的阻塞点，其余问题都可以在排查过程中边做边答。

## 知识来源

- prefill 与 decode 两阶段的行为差异、分页 KV cache 的块表与槽位映射、块回收与脏数据、A/B/A 与交错批验证：vLLM 的 PagedAttention 公开论文（SOSP 2023）与开源实现中公开的接口约定；本仓 [`model-infer-kvcache`](../../skills/model-infer-kvcache/SKILL.md) 已沉淀同一套概念
- 变长布局的累积长度数组语义、`q_len ≠ kv_len` 时 causal mask 的右下对齐规则：FlashAttention 开源实现公开的接口约定
- RoPE 的两种排布（interleaved / half-split）互不兼容、位置偏移与长上下文缩放：RoFormer 论文与 HuggingFace Transformers 公开的建模实现
- bf16（8 位尾数）与 fp16（11 位尾数）的机器精度、fp16 的最大可表示值 65504、累加器精度对长序列的影响：IEEE 754 与 bfloat16 的公开定义
- 误差度量的选择（最大绝对/相对误差、余弦相似度、相对 L2 各自的盲区）：数值计算的通用实践
- "用误差增长曲线的台阶定位首个差异点"而非用绝对阈值：数值调试的通用方法论
- MoE 专家权重加载不完整导致少数 token 异常：稀疏专家模型路由机制的直接推论，与具体实现无关
