# 量化接入

> 组 1。等级 **B**（底层能力在通用生态里成熟，需要确认你的栈提供哪一个）。

## 一句话结论

**接入量化权重这件事的流程是通用的，唯一真正难的一步是"证明量化真的生效了"——因为框架里普遍存在静默回退到 fp16 的兜底分支，它不报错，而跑通、输出正常、显存看起来少了一点，这三件事全都不能作为生效的证据。**

## 当前状态

| 现在能做 | 还差什么 |
|---|---|
| 本文的六步工作流、生效验证的四条证据、收益评估的口径，全部与芯片无关 | 不知道你的栈支持哪些量化格式。`hardware-profiles/` 的 `kernels.quantization` 整节都是 `null` |
| 量化产物的契约检查清单可以立刻对着一份真实产物过一遍 | 不知道权重要不要特殊内存布局，也就不知道要不要写 post-load 转换 |
| 「kernel 名证据」这条验证依赖 profiler | 依赖[性能数据采集](perf-profiling.md)的 T1 层。没有它时只剩三条证据 |

## 范围

**只覆盖"接入已经量化好的权重"**，不覆盖设计量化算法、做量化感知训练、或自己跑校准生成量化产物。也就是说，输入是一份别人产出的量化权重，目标是让它在你的卡上正确且高效地跑起来。

KV cache 量化是独立的另一条线（它影响的是显存而非权重），本文只在收益评估一节提到它，不展开。

## 工作流

### 1 · 量化产物契约检查

**在写任何代码之前，先把产物读一遍。** 这一步跳过的代价是后面每一步都在猜。

- [ ] **格式与超参**：量化方法标识、位宽、是否对称、group_size、是否有权重重排（act-order 一类）
- [ ] **权重张量的 shape 与方向**：很多格式按 `[in_features, out_features]` 存，而 PyTorch 的 `Linear.weight` 是 `[out_features, in_features]`。转置搞反不会报错，只会输出乱码
- [ ] **低位宽的打包方式**：int4 通常几个一组塞进一个 int32 或一个字节。**每个容器装几个、高低位谁在前，这两件事没有标准**，必须从产物的 shape 反推并与文档核对
- [ ] **scale / zero_point 的形状**，由此反推粒度：标量是 per-tensor；`[out_features]` 是 per-channel；`[out_features, in_features/group_size]`（或其转置）是 per-group
- [ ] **是否包含激活量化参数**。有就是静态激活量化，没有则激活要么保持高精度，要么运行时动态算 scale
- [ ] **哪些层没被量化**。通常 lm_head、embedding、各类 norm、MoE 的 router 会保留高精度，这些层的参数量要单独算进显存预算

**最后做一次产物自检**：挑一两个层把量化权重反量化回 fp16，与同一模型的原始 fp16 权重算余弦相似度，应当 > 0.99。这一步能挡掉"产物本身就是错的"这种最浪费时间的情况——如果省了这步，后面所有排查都会指向错误的方向。

### 2 · 模型结构匹配

把产物里的层名与模型里的层名做一次完整的双向对照，**两边都不允许有孤儿**。产物里有而模型里没有，说明模型结构版本不对；模型里有而产物里没有，要确认它是故意保留高精度还是漏了。

这一步真正的难点是**合并层**。推理实现普遍会把 q/k/v 合成一个线性层、gate/up 合成一个，而量化产物往往是按原始的分离层量化的：

| scale 粒度 | 沿输出维拼接（q/k/v 合并、gate/up 合并） | 沿输入维切分（row-parallel） |
|---|---|---|
| per-tensor | **不能直接拼**。三个层的 scale 不同，拼完必须重选一个 scale，精度会掉。要么不合并，要么回到产物侧重新量化 | 分片的 partial sum 必须在高精度域累加后再加和 |
| per-channel | 安全，scale 直接 concat 即可（每个输出通道独立） | scale 不随输入维切分而变，安全 |
| per-group | 沿输出维拼接安全 | **group 不能跨切分边界**，要求 `in_features / TP 并行度` 是 `group_size` 的整数倍 |

MoE 还要多一层：专家权重通常是 `[num_experts, out, in]` 的三维张量，scale 也要带专家维；而且能不能量化取决于**grouped GEMM 有没有量化版本**，这与普通 Linear 的量化支持是两件独立的事。

### 3 · 量化层替换

用一个量化线性层替换原来的 `nn.Linear`，对外保持同样的 forward 签名与 dtype 契约（输入 fp16/bf16，输出同 dtype）。

**替换时机很重要：在模型构造之后、权重加载之前替换。** 先建出 fp16 权重再替换掉，会在加载期产生一次完整的 fp16 显存峰值——这是"明明量化了，加载的时候还是 OOM"最常见的原因。用 meta device 之类的延迟初始化手段可以彻底避免这个峰值，具体写法取决于你的栈怎么接的 PyTorch。

另外两条：
- 保留一个全局开关，可以整体退回 fp16 路径。后面每一步对拍都要用它
- lm_head 通常不量化。它的输出维是词表大小，per-channel scale 的数量很大，且它直接决定采样结果，对精度最敏感

### 4 · 权重加载与 post-load 处理

- 加载路径**不做反量化**。一旦在加载时反量化成 fp16 存下来，显存收益直接归零，而功能完全正常——这是最隐蔽的一种失败
- 很多量化 GEMM 要求权重按特定的 interleave 或 swizzle 排布。这类转换必须放在一个**显式的 post-load 钩子**里，在所有权重都加载完成之后统一执行
- **为什么必须是 post-load 而不是边加载边转**：张量并行下权重是逐分片加载的，布局转换只有在整片拼完之后做才正确
- scale 的 dtype 可能需要提升（有些算子要求 fp32 scale）

这一步漏掉 post-load 钩子的表现是：加载过程一切正常，第一次前向时要么报一个形状或对齐相关的错，要么直接输出乱码。排查时很容易误判成算子有 bug。

### 5 · 真实生效验证

**这是最容易被跳过的一步**，因为跳过它不会有任何症状：模型跑通了、输出读起来正常、显存好像也少了一点。但框架里普遍存在"检测到不支持就反量化回 fp16 再算"的兜底分支，它通常只打一条 debug 级日志。

下面四条证据**互相独立，必须都过**。任何一条单独成立都不足以证明生效。

**证据 A · 显存**

```
理论权重字节 = Σ_量化层 (参数量 × 位宽 / 8)
             + Σ_量化层 (scale 与 zero_point 的字节)
             + Σ_非量化层 (参数量 × 2)
```

加载完成后实测权重占用，与理论值比：

| 偏差 | 含义 |
|---|---|
| 实测 ≈ 理论（10% 以内） | 通过 |
| 实测显著高于理论 | 有层没被量化，或者存了一份反量化后的 fp16 副本 |
| 实测显著低于理论 | 有层根本没加载。去看[精度诊断](infer-precision-debug.md)的根因 8 |

**证据 B · kernel 名**

用[统一 schema](../../tools/profiler_adapter/README.md) 把 profiler 产物转一遍，按 kernel 名分桶，检查三件事：

- 量化 GEMM 的 kernel 确实出现了，调用次数约等于 `量化层数 × 步数`
- fp16 GEMM 的调用次数相对未量化版本显著下降
- **没有出现大量反量化 / 类型转换 kernel**。出现了就说明在反量化之后用 fp16 算，收益只剩显存

这是最直接的一条证据，但它依赖[性能数据采集](perf-profiling.md)的 T1 层。

**证据 C · 权重 dtype**

遍历所有权重打印 `名字 / dtype / shape`，量化层应当是整型（int8，或打包进 int32/uint8 的 int4），不是 float16。

**遍历必须同时覆盖 parameters 和 buffers。** 很多实现把量化权重注册成 buffer 而不是 parameter（因为它不参与梯度），只看 parameters 会把它们全部漏掉，得出"一个量化层都没有"的错误结论。

**证据 D · 数值差异（反直觉但最严）**

量化模型与 fp16 模型的输出**应当有可测量的差异**。如果两者逐位完全一致，说明根本没走量化路径。

这条证据的价值在于它可以**逐层做**：对比每一层输出与 fp16 版本的最大绝对误差，量化层应当有非零误差，**误差恰好为 0 的层就是没生效的层**。前三条证据都可能被"部分层生效"蒙混过去，这一条不会。

**补充的性能旁证**：权重位宽减半时 decode 延迟应当明显下降（decode 是访存受限的，权重读取占主导）。完全没变就要怀疑静默回退。注意这只是旁证，不能替代前四条。

**最后别忘了精度验收**：量化后输出一定会变，需要事先定好可接受范围。至少跑一组固定用例看困惑度或下游任务指标，不要用"读起来通顺"当验收标准。

### 6 · 收益评估

见下一节。核心原则：**先定目标负载，再评估收益**，否则测出来的数字无法支撑任何决策。

---

## 收益要多维度看

| 维度 | 怎么测 | 只看它会错在哪 |
|---|---|---|
| 权重显存 | 加载完成后的实测占用 | 长上下文场景下 KV cache 才是大头。权重降 50%，总显存可能只降 15% |
| KV cache 显存 | 块池能分配多少块 | 只有 KV cache 量化才直接影响它，权重量化对它是零。但权重腾出的显存会转化成更多块——**这是权重量化的间接收益，很容易漏算** |
| prefill 吞吐 | 首 token 时延、prefill 阶段的 tokens/s | prefill 是计算受限的，低位宽权重要在 GEMM 里反量化，**有可能更慢**。只看这个会误判成"量化没用" |
| decode 延迟 | 每 token 时延 | decode 是访存受限的，收益最大。只看这个会高估整体收益 |
| 最小部署卡数 | 权重 + KV cache + 峰值激活 + 通信缓冲能否塞进 N 卡 | **这往往才是真实的商业收益**。显存降 30% 但仍需同样卡数等于收益为 0；降到能让 4 卡变 2 卡，就是成本减半 |

端到端收益不是各项的加权平均，要按目标负载的 token 构成算：

```
Δt_总 = prefill_tokens × Δt_每 prefill token + decode_tokens × Δt_每 decode token
```

一个长 prompt、短输出的摘要类负载，和一个短 prompt、长输出的对话类负载，**同一个量化方案的端到端收益可能符号都相反**。所以评估的第一步永远是确定目标负载的 prefill 与 decode token 比例。

另外两条容易混淆的地方：

- **吞吐和延迟不是一回事。** 量化腾出显存 → 可以提高并发 → 吞吐上升，但单请求延迟可能不变甚至变差（排队变长）。报收益时必须说清是哪一个
- **对比必须同口径**：同样的 batch、序列长度、并发度，剔除首步。这与 [perf-breakdown](../../skills/model-infer-perf-breakdown/SKILL.md) Step 5 的对比纪律是同一条

## 量化与算子融合的冲突

根本原因：融合算子的输入输出 dtype 契约通常写死为 fp16/bf16，而量化 GEMM 的输出是整型累加结果。要把它喂给下游融合算子就得先做一次 requant/dequant，而这次转换本身就是一次完整的读写——恰好抵消掉融合想省下的那次读写。

三种具体冲突：

1. **量化 GEMM 的 epilogue 不支持融合 bias 与激活** → bias 和激活退化成独立 kernel，多两次中间张量读写
2. **归一化+残差一类的融合算子只接受浮点输入** → 量化层的输出必须先转回 fp16，转换开销可能超过融合收益
3. **自定义量化算子可能让图捕获或编译失败** → 与[图模式](../../skills/model-infer-graph-mode/SKILL.md)的收益冲突。表现为量化之后图模式的 graph break 数量上升

何时回退哪一边：

| 情形 | 保哪个 | 理由 |
|---|---|---|
| 该层权重很大且访存受限（大 FFN、MoE 专家） | **保量化** | 权重读取是主要开销，位宽减半的收益远大于一次中间张量读写 |
| 该层很小、融合省的主要是启动开销（norm + 残差） | **保融合** | 这类层的权重本来就小，量化省不下多少 |
| 两者都想要 | 让量化算子的 epilogue 支持该融合 | 这是正解，但属于算子库建设，不是接入层能解决的 |
| 判断不了 | **实测两种组合** | 不要靠推理。两个方案各跑一次性能拆解直接比 |

**一条硬纪律：量化和融合的改动不要同时上线。** 先单独验证量化生效，再单独验证融合生效，最后才组合。组合之后出问题，无法判断是哪一边——而这两边的回退方式完全不同。

## 卡在哪

三件事必须先知道，否则工作流的第 1、3、4 步都只能猜：

| 需要知道 | 对应 profile 字段 | 不知道的后果 |
|---|---|---|
| 支持哪些量化格式 | `kernels.quantization.supported_formats` | 不知道能接什么产物。权重低位宽+激活高精度、权重与激活都低位宽、fp8，三类对硬件的要求完全不同 |
| 权重要不要特殊内存布局 | `kernels.quantization.weight_layout_requirement` | 不知道要不要写 post-load 转换，也不知道转换在主机侧还是设备侧做 |
| 缩放因子支持什么粒度 | 目前没有对应字段 | 不知道能接什么产物，也无法判断张量并行的切分约束 |

`kernels.quantization` 一节的 `int8_gemm` / `fp8_gemm` / `int4_gemm` / `dynamic_quant` 目前全是 `null`，整节 `_status: unknown`。

**profile 里没有、建议补上的字段**：

- 低位宽权重的打包约定（每个容器装几个、高低位顺序）
- 量化 GEMM 的累加器 dtype 与 requant 路径
- 是否支持权重重排索引（act-order 一类）
- 量化 GEMM 的 epilogue 支持哪些融合（决定上一节的冲突怎么解）
- 是否存在 KV cache 量化算子（独立于权重量化的另一条线）
- grouped GEMM 有没有量化版本（直接决定 MoE 能不能量化）

## 需要你拍板的问题

| # | 问题 | 回答后能解锁什么 |
|---|---|---|
| 1 | 你的算子库支持哪些量化格式（权重位宽 × 激活精度的组合）？ | 决定能接什么产物。这是唯一的硬阻塞，其余问题都建立在它之上 |
| 2 | 缩放因子支持哪些粒度（per-tensor / per-channel / per-group），group_size 有哪些合法取值？ | 决定能接什么产物，以及张量并行切分时 `in_features / TP` 要满足什么整除条件 |
| 3 | 量化权重需要特殊内存布局吗？转换在主机侧还是设备侧做？ | 决定要不要写 post-load 钩子。为是而没写，表现是首次前向报错或输出乱码 |
| 4 | 量化 GEMM 的累加器是什么 dtype，requant 在算子内还是算子外做？ | 决定输出 dtype 契约，也决定与下游融合算子怎么衔接 |
| 5 | 量化 GEMM 的 epilogue 支不支持融合 bias 和激活？ | 决定「量化与融合的冲突」那一节要不要真的做取舍，还是可以两者兼得 |
| 6 | grouped GEMM 有没有量化版本？ | 决定 MoE 模型能不能量化。MoE 的专家权重通常是显存占比最大的部分，这一项为否的话量化收益会大打折扣 |
| 7 | 你的目标负载里，prefill 与 decode 的 token 比例大致是多少？ | 决定收益评估的口径。这个比例不定，测出来的任何数字都无法支撑决策 |
| 8 | 框架里"不支持就反量化回 fp16"的兜底分支存在吗？打不打日志？ | 决定生效验证要做到多严。有兜底而不打日志时，四条证据一条都不能省 |

**回答顺序建议**：1 → 2 → 3。前三题答完就可以开始接入；第 7 题要在评估收益之前答，否则做完没法判断成败。

## 知识来源

- 权重量化的常见产物组织方式（低位宽权重打包、scale 与 zero_point 的粒度、是否带权重重排索引）：GPTQ、AWQ 等公开论文与其开源实现中公开的产物格式约定
- per-tensor / per-channel / per-group 三种缩放粒度的定义与取舍：神经网络量化的公开综述与 PyTorch 量化文档
- 合并层（q/k/v、gate/up）与张量并行切分对缩放粒度的约束：线性代数的直接推论——按输出通道独立的 scale 可沿输出维自由拼接，per-tensor 不可
- decode 阶段访存受限、prefill 阶段计算受限，以及由此导致的量化收益在两阶段方向相反：roofline 模型（Williams et al., 2009）在自回归推理上的直接应用，另见[性能数据采集](perf-profiling.md)
- 推理框架中"不支持则反量化回高精度"的兜底实现模式，以及由此产生的静默回退：vLLM、HuggingFace Transformers 等开源推理栈公开代码中的常见结构
- KV cache 显存与权重显存在长上下文下的占比关系：vLLM 的 PagedAttention 公开论文（SOSP 2023）
- 对比实验的同口径要求与首步剔除：性能测试的通用工程实践，与本仓 [`model-infer-perf-breakdown`](../../skills/model-infer-perf-breakdown/SKILL.md) 一致
