# 训练出现 NaN / Inf

> 能力等级 **C**。阶段划分法现在就能用，`detect_anomaly` 能兜住一部分；精确定位首个非有限点需要[精度工具栈](_precision-toolchain.md)的阶段 1，追溯放大起点需要阶段 3。

## 一句话结论

**loss 变 NaN 的位置几乎一定不是 NaN 产生的位置**——NaN 的传染性让下游全部变 NaN、信息量归零，要找的是"输入全有限、输出出现非有限"的那**一次**算子调用，而它往往也只是表象，真正的根因在它上游某个"还是有限值、但量级已经不对"的地方。

## 当前状态

**待建设。** 三件事的可用度差别很大：

| 能力 | 现在 | 建成后 |
|------|------|--------|
| 把问题划到前向 / 反向 / 优化器 | **已可用**，只要四个检查点，手工就能做（第三节） | 不变 |
| 定位首个非有限转换点 | 只能靠二分，一个 step 要几分钟时成本不可接受 | 工具直接给出（[工具栈阶段 1](_precision-toolchain.md#阶段-1基于-pytorch-hook-的统计摘要-dump)） |
| 追溯到异常放大起点 | 做不到 | 需要历史统计 + 上游张量，[阶段 3](_precision-toolchain.md#阶段-3定向张量-dump-与根因定位) |
| 捕捉几百步才一次的偶发 | 做不到 | 需要触发式环形缓冲，阶段 3 的一个独立子能力 |

## 一、关键区分：最终 NaN ≠ NaN 首发位置

最常见的错误做法是在 loss 变 NaN 的地方加断点。loss 是整个计算图的汇点，NaN 传到这里时已经过了成百上千个算子。

而且 NaN 的传播特性让情况更糟：按 IEEE 754，几乎所有浮点运算只要有一个 NaN 输入就输出 NaN。所以 **NaN 具有极强的传染性和零信息量**——一旦出现，下游全是 NaN，从结果完全看不出来源。观察到一百个位置是 NaN，和观察到一个位置是 NaN，信息量是一样的。

要找的是**首个非有限值的产生点**：输入全有限、输出出现非有限的那一次调用。这个定义的好处是**可机器判定**，而"loss 是 NaN"不是——它只是一个已经发生的事实。

### 先分清 inf 和 nan

这两者的成因不同，查的方向也不同：

| 值 | 典型成因 | 第一反应 |
|----|---------|---------|
| `inf` / `-inf` | 溢出（超出 dtype 表示范围）、除以 0 | 查 fp16 溢出、查分母 |
| `nan` | `inf - inf`、`0 * inf`、`0/0`、`inf/inf`、负数开方、`log(非正数)` | 查上游是否已有 inf，查未定义的数学操作 |

dtype 的差别在这里很关键。fp16 的表示上限约 65504，溢出门槛很低；bf16 的指数范围与 fp32 相同（上限约 3.4e38），几乎不会因为"数值有点大"就溢出，但尾数只有 8 位，更容易出现精度不足导致的下溢归零，进而 `0/0`。

由此得到一条很有用的推论：**bf16 训练出现 inf 比 fp16 严重得多**。fp16 的 inf 可能只是动态范围不够，是可以靠 loss scaling 解决的工程问题；bf16 出现 inf 说明数值真的到了 1e38 量级，这几乎一定是逻辑错误。

## 二、三种角色：放大起点 / 首个转换点 / 传播放大器

一次 NaN 事故里涉及的位置分三种角色，处置方式完全不同。把它们混为一谈是这类问题排查效率低的主要原因。

| 角色 | 特征 | 为什么重要 | 处置 |
|------|------|-----------|------|
| **异常放大起点** | 输出**仍是有限值**，但量级远超该位置的历史分布（如激活 max 从 1e2 跳到 1e20） | 真正的根因所在 | 查该算子的输入、超参（lr 过大、warmup 过短）、是否缺 norm、数据里是否有极端样本 |
| **首个非有限转换点** | 输入全有限，输出出现 inf/nan | 工具能机器判定的**唯一锚点** | 从这里向上游回溯找放大起点 |
| **传播放大器** | 输入已含非有限值，输出自然也含 | 零信息量 | 忽略。必须被工具过滤掉，否则会淹没前两类 |

典型链条是这样的：某处 attention score 因为 scale 写错或缺了 `1/sqrt(d)`，量级到了 1e4（**放大起点**，仍有限）→ 后面的 `exp` 溢出成 inf（**首个非有限点**）→ 之后全是 nan（**传播**）。真正要改的是第一个位置，但工具只能自动找到第二个，第一个要靠人从第二个往上看。

这直接推出一条具体的工具需求，应当写进[工具栈的验收标准](_precision-toolchain.md#五验收标准)：**工具的输出不能只是首个非有限点，必须同时给出该点上游若干个调用的统计摘要**，让人一眼看出量级从哪里开始不对。只报一个点的工具，用起来会发现还是得手工往上翻。

异常放大的判据是**和历史比，不是和绝对阈值比**。同一位置在过去 N 步的 max 分布是最好的参照系。如果只有事故那一步的数据，退而求其次：和同层其它位置比、和相邻层比——transformer 各层结构相同，某一层的激活量级显著偏离其它层本身就可疑。

## 三、阶段划分法

用少量检查点把问题划到前向 / 反向 / 优化器。核心分界点是 **logits 的有限性**。

| 观察 | 结论 | 下一步 |
|------|------|--------|
| logits 已含非有限值 | 问题在**前向** | 在前向路径上按层二分 |
| logits 有限，loss 非有限 | 问题在 **loss 计算本身** | 查 label 越界、`log(0)`、整行被 mask 导致 softmax 分母为 0、`ignore_index` 配置 |
| logits 与 loss 都有限，某些梯度非有限 | 问题在**反向** | 在反向路径上按层二分；注意反向算子通常比前向测试得少 |
| 梯度全有限，更新后的权重非有限 | 问题在**优化器更新** | 查 lr、eps 位置、weight decay、二阶矩开方、scaler 的 unscale |
| 本步一开始输入就带着非有限值 | 问题在**数据**或**上一步** | 查数据管线；查上一步是否已经把权重写坏 |

这个表的实用价值在于：它只需要 logits、loss、全局梯度范数、权重有限性这四个量，**而这四个量即使没有任何 dump 工具也能手工打出来**。所以阶段划分法现在就能用，而且应该是任何 NaN 问题的第一步。

最后一行值得单独说。**权重一旦被污染，之后每一步的所有输出都是 NaN**，看起来就像"每一步都在产生 NaN"。所以要在每步**开始时**检查权重的有限性：如果 step N 开始时权重已经坏了，真正的事故发生在 step N-1 的优化器更新，在 step N 里怎么找都找不到。

还有一个便宜的常驻防线值得一提：**在梯度 all-reduce 之后检查全局梯度范数是否有限**，不有限就报错或跳步。Megatron-LM 一类框架内置了这个开关。它的成本是每步一次标量 reduce，可以忽略，但能把"事故发生在哪一步"精确记录下来，而不是等到几十步后 loss 变 NaN 才发现。建议默认开启。

## 四、假阳性过滤

不做过滤的话，扫描工具会报出大量合法的非有限值，噪音淹没信号，几次之后就没人看它的输出了。

| 假阳性来源 | 表现 | 为什么合法 | 过滤方式 |
|-----------|------|-----------|---------|
| **causal / padding mask** | attention score 里大量 `-inf`（或 `-1e9` 之类的大负数） | mask 的实现就是把被遮位置置为负无穷，softmax 后变 0 | 把 mask 相关算子加白名单，或只在 softmax **之后**检查。注意 `-inf` 合法但 `nan` 不合法 |
| **未初始化占位张量** | `torch.empty` 创建的 buffer 在被写入前含任意位模式，可能恰好是 NaN | 它本就不该被读 | 区分"被消费的输入"和"仅作输出 buffer 的张量"，只检查前者 |
| **通信覆盖前的野值** | all-gather / all-to-all 的接收缓冲在通信完成前含旧值或垃圾 | 异步通信下在同步点之前读是未定义的 | 只在通信的 wait 之后检查 |
| **GradScaler 的正常 inf** | 混合精度下梯度 inf，scaler 跳过该步并降 scale | 这是 GradScaler 的正常工作方式 | 见第六节 |
| **优化器状态初值** | Adam 的二阶矩第一步是 0，`sqrt(0)` 作分母 | 实现里有 eps 兜底 | 优化器内部状态不纳入常规扫描，单独处理 |
| **故意的 inf 哨兵** | 某些实现用 `inf` 表示"无效"（top-k 填充、beam search 中已结束的序列、MoE 容量溢出的 token） | 语义如此 | **这是模型相关的，必须允许配置白名单**。工具不可能内置完整清单 |
| **`ignore_index` 的被忽略位置** | 被忽略的位置可能保留未定义值 | 它们不参与 reduce | 检查 reduce 之后的值 |

过滤的设计原则是：**默认全报，但分级标注，不要直接丢弃**。因为"已知合法"的位置有时恰恰就是出问题的地方——最典型的是 attention mask：mask 产生的 `-inf` 是合法的，但如果某一行被**全部**遮住，softmax 的分母就是 0，结果是 NaN，这时 `-inf` 合法而 NaN 是真 bug。如果工具把整个 mask 路径直接加黑名单，这个 bug 就永远看不到了。变长序列、packing、滑动窗口 attention 的实现里，"某行被全遮"是一个真实存在的边界情况。

## 五、PyTorch 原生手段能覆盖多少

### `torch.autograd.detect_anomaly`

**能答的：**
- 反向传播中哪个 backward function 产生了 NaN
- 给出该 function 对应**前向操作的 Python 调用栈**——这是它最有价值的地方，能指到源码行

**不能答的：**

| 限制 | 影响 |
|------|------|
| 只管反向 | 前向产生的 NaN 它不管（除非后来反向里也出现）。而前向出 NaN 的情况不少 |
| 不给数值 | 只说"这里出了 NaN"，不说输入是多少、有多少元素是 NaN、量级分布如何。无法区分第二节的三种角色 |
| 定位粒度是 autograd 节点 | 报的是 `AddmmBackward` 这类名字，你想知道的是"第 12 层的 down_proj" |
| 不做跨运行比对、不做上游回溯 | 拿不到"量级从哪里开始不对" |
| 开销巨大 | 它为每个张量记录前向调用栈。官方文档明确说明只应在调试时使用，大模型上全程开启基本不可行 |
| **分布式下很麻烦** | 每个 rank 独立抛异常；异常抛出会打断集合通信，其它 rank 卡在 all-reduce 上直到超时，真正的错误信息被通信超时淹没 |

最后一条在实践中最致命，它基本上把 `detect_anomaly` 限制在**单卡小规模复现**的场景。如果你的 NaN 只在多卡大规模下出现，这条路直接走不通。

### 其它原生手段

- **`torch.isnan` / `isinf` / `isfinite` 手工撒点**：能用，但每次检查都是一次 reduce 加一次 D2H 同步。覆盖率和成本不可兼得——撒得密就慢到不能跑，撒得疏就只能二分。这实际上就是在手工实现[工具栈阶段 1](_precision-toolchain.md#阶段-1基于-pytorch-hook-的统计摘要-dump)，只是没有命名、没有落盘、没有自动化。
- **`register_full_backward_hook` 手工检查梯度**：可行，同上。
- **`torch.nan_to_num`**：这是**止血不是诊断**。它让训练继续跑，但掩盖了问题，而且掩盖之后模型学到的东西是否还有意义无人能保证。只在已经确认某位置的 NaN 可接受（比如确认是 mask 导致且下游会被正确屏蔽）时使用，绝不要当作修复手段。
- **框架内置的梯度非有限检查**：见第三节，便宜且有效，建议常驻。

**结论**：原生手段足够回答"出事了"和"大概在反向的哪一块"，不足以回答"首个产生点在哪、当时的数值是什么、量级从哪里开始不对"。后三个问题恰恰是修复所需要的。

## 六、混合精度：哪些 inf 是正常的

GradScaler 的工作方式是：前向 loss 乘一个 scale 因子，反向得到放大的梯度，优化器步之前 unscale 回来；如果 unscale 后发现 inf/nan，**跳过本步的参数更新并把 scale 减半**；连续若干步无 inf 则把 scale 翻倍。

所以**训练早期偶尔出现 inf 并跳步是 GradScaler 的正常工作方式，不是 bug**——它在主动探测可用的最大 scale。判别标准：

| 现象 | 判定 |
|------|------|
| 初期若干次跳步，之后 scale 稳定在某值，loss 正常下降 | 正常，不用管 |
| scale 单调下降到最小值仍持续跳步 | **异常**。梯度本身含非有限值，与 scale 无关 |
| 跳步率持续偏高（经验上持续高于百分之几） | **异常**。有效的优化步数被显著削减，即使不报错训练也在变慢 |
| scale 稳定，某一步突然 inf 之后恢复 | 可疑。查当时的 batch，可能是极端样本 |
| 用 bf16 且没有 scaler，仍出现 inf | **真 bug**。bf16 动态范围与 fp32 相同，正常训练不该溢出 |

两个相关的陷阱：

**loss scale 会放大本来不溢出的中间量。** 某些反向实现里有中间的平方或长程累加，scale 过大时这些中间量先溢出，表现为"梯度 inf"，但降低 scale 就好了。这类情况 scaler 的自动调节会自己收敛，不是 bug。判别方法是看降低 scale 后是否稳定。

**unscale 与梯度裁剪的顺序。** 必须先 unscale 再 clip，否则 clip 的阈值作用在放大后的梯度上，等于没裁。顺序错了的表现未必是 NaN，而是"训练偶尔爆炸"，更难查。使用 `GradScaler` 时 PyTorch 提供了显式的 `unscale_` 接口正是为此。

## 七、有工具后的流程

1. 开常驻摘要采集（含**非有限值计数**，不只是布尔标志——计数能区分"一个元素坏了"和"整个张量都坏了"，这两者的成因不同），跑到事故步。
2. 工具按执行顺序给出**首个"输入全有限、输出非有限"的调用**。
3. 套第四节的假阳性白名单过滤。
4. 看该点**上游 N 个调用的 max 曲线**，找异常放大起点。
5. 在放大起点上开定向张量 dump，重跑到该步，取出完整输入。
6. 分析误差的空间分布：是少数元素异常（指向数据问题或个别 token），还是整体量级漂移（指向超参、缺 norm、scale 写错）。
7. 构造脱离训练框架的最小复现，交给算子团队或直接改超参。

**偶发事故需要额外能力。** 如果几百步才出一次，上面的流程里"重跑到该步"这一步就不成立了——你不知道下次在哪一步。解法是**触发式环形缓冲**：平时只采摘要，内存里滚动保留最近 K 个调用的完整张量，一旦扫描到非有限值就把整个缓冲落盘。这是[工具栈阶段 3](_precision-toolchain.md#阶段-3定向张量-dump-与根因定位) 里一个独立的、成本不低的子能力（要常驻一块可观的内存），是否要做取决于你的 NaN 是稳定复现还是偶发——这是下面的拍板问题 5。

## 八、需要你拍板的问题

| # | 问题 | 回答后能解锁 |
|---|------|------------|
| 1 | 主要用 fp16 + GradScaler 还是 bf16？ | 确定 inf 的判别基线。bf16 下的 inf 几乎都是真 bug，可以跳过整条 loss scaling 排查分支 |
| 2 | 你的模型实现里有哪些地方用 inf 或极大负数作哨兵（mask、top-k 填充、MoE 容量溢出、beam search）？ | 假阳性白名单的初始内容。这份清单工具无法自动推断，只能由你提供 |
| 3 | 训练框架是否已有"梯度范数非有限就跳步/报错"的开关？ | 常驻防线是否已存在。没有的话这是成本最低、收益最直接的一个补丁 |
| 4 | `detect_anomaly` 在你的后端上能否正常工作（异常正确抛出、调用栈完整）？ | 单卡小规模复现时能否用原生手段兜底，决定工具建设的紧迫性 |
| 5 | 当前的 NaN 是稳定复现还是偶发？偶发的话大致多少步一次？ | 决定要不要建触发式环形缓冲 dump——这是阶段 3 里一个独立的、内存成本不低的子能力 |
| 6 | 出现 NaN 时能否拿到当时的 batch 数据（dataloader 是否可按 step 重放）？ | 能否排除数据侧的极端样本。不能重放的话，这条最常见的真因无法验证 |
| 7 | NaN 是单卡就出现，还是只在多卡下出现？ | 多卡才出现的话，嫌疑直接指向通信路径（接收缓冲未就绪、规约溢出），排查路径完全不同 |

## 九、知识来源

- **IEEE 754** 浮点标准：inf 与 nan 的产生规则（溢出、除零、`inf-inf`、`0*inf`、`0/0`）、NaN 在算术运算中的传播规则、fp16 与 bf16 的指数位与尾数位分配及由此决定的表示范围
- **PyTorch 官方文档**：`torch.autograd.detect_anomaly` / `set_detect_anomaly`（功能、它记录前向调用栈的机制、以及只应用于调试的官方开销警告）；`torch.amp` 与 `GradScaler`（loss scaling 的自适应机制、跳步行为、`unscale_` 与梯度裁剪的正确顺序）；`torch.isfinite` / `isnan` / `isinf`；`torch.nan_to_num`
- **Micikevicius et al.**, *Mixed Precision Training* (ICLR 2018)：loss scaling 的动机与动态调整策略——"训练早期的跳步是正常探测过程"这一判断的出处
- **bfloat16 的设计意图**（Google Brain 公开材料与各家硬件文档）：保留 fp32 的指数范围、牺牲尾数精度——"bf16 出现 inf 比 fp16 严重"这一推论的依据
- **开源项目实践**：Megatron-LM 的梯度非有限值检查开关（在梯度归约后检查全局范数）；主流 attention 实现中 causal / padding mask 使用负无穷填充的通行做法，以及由此产生的"整行被遮导致 softmax 分母为 0"边界情况
