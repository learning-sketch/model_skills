# 训练结果不可复现

> 能力等级 **C**。方法论部分（随机性契约）现在就能用；定位到首个差异点需要[精度工具栈](_precision-toolchain.md)的阶段 2。

## 一句话结论

"不可复现"里有一大半不是 bug，是**随机性契约没有被完整固定**——这部分现在就能靠一份 checklist 查完；剩下的一小半是真问题（算子内部竞态、通信规约顺序、编译器浮点重排），它们需要工具才能定位，而且是自研芯片最容易踩的部分。

## 当前状态

**待建设。** 契约检查这一层不依赖任何工具，本文的第二节写成了可直接执行的清单。真正缺的是**首个差异点定位**：两次运行的产物能按调用实例对齐比对。这需要[精度工具栈](_precision-toolchain.md)建到阶段 2。

另外有一个前置未知数：`torch.use_deterministic_algorithms(True)` 在你的后端上到底做了什么。如果它只是被静默忽略，那么"我已经开了确定性开关"这句话不构成任何保证，下面所有流程的起点都要重设。这是本文结尾第 1 个拍板问题。

## 一、问题定义

### 先定义什么叫"一致"

| 级别 | 判据 | 用途 |
|------|------|------|
| **逐位一致** | 所有张量逐位相同 | 本文档的目标。唯一能机器自动判定、不需要人拍阈值的标准 |
| 数值接近 | loss 曲线在容差内重合 | 训练级验收，属于[标杆不一致](train-precision-mismatch.md)的范畴 |
| 统计等价 | 最终指标相当 | 科研结论级别，与调试无关 |

本文只讨论第一种。问题的标准形态是：**固定了输入、初始权重、随机种子，开启了确定性算法开关之后，两次运行仍然不逐位一致**。这是一个 bug——除非能明确归因到第二节契约里某个未被固定的来源。

### 为什么这个领域的优先级高于另外两个

**可复现性是其它一切精度调试的前提。** 如果目标平台自己两次跑都不一样，那么：

- 与标杆的任何差异都无法归因——你分不清这个差异是真实现问题，还是这次运行恰好的随机抖动
- 逐层比对本身就不成立——比对要求两侧调用序列可对齐，而不可复现往往意味着序列本身在变
- NaN 的定位会变成撞运气——复现一次要跑多少次是未知的

所以三件套的建设顺序建议是：**先可复现，再 NaN，再标杆对齐**。

### 一条容易被跳过的分界

在开始查之前，先回答一个问题：**不一致是"每次都不一样"还是"偶尔不一样"？**

每次都不一样，通常是契约层面的遗漏（某个种子没固定），查起来快。偶尔不一样——尤其是概率很低——几乎一定是执行层的真问题（竞态、未初始化内存、通信算法自适应），查起来慢，而且[观察者效应](_precision-toolchain.md#决策-6观察者效应)会严重干扰。两者的处置路径不同，不要混在一起查。

## 二、随机性契约 checklist

这一节是纯方法论，不依赖任何工具，**现在就能逐条执行**。按组织顺序逐项确认，每项都有一个明确的"已固定/未固定/不适用"的答案。

### A. 种子与 RNG 状态

| # | 检查项 | 常见疏漏 |
|---|--------|---------|
| A1 | `random.seed()` | 第三方库（如某些 tokenizer、数据增强）会用 Python 内置 random |
| A2 | `np.random.seed()` | 数据预处理里大量使用 |
| A3 | `torch.manual_seed()` | 只设这个不够，设备侧 RNG 可能独立 |
| A4 | 设备 RNG 的 `manual_seed_all` 等价物 | **你的后端是否有独立的设备侧 RNG？它的 offset 怎么推进？** 这是拍板问题 6 |
| A5 | 多 rank 的**种子派生规则** | 见下文 |
| A6 | checkpoint 是否保存并恢复 RNG 状态 | 断点续训后轨迹与不中断运行不一致，最常见的"假性不可复现" |

关于 A5：多 rank 下不存在"全部用同一个种子"或"全部用不同种子"这种统一答案，规则是**按用途分**。需要各 rank 一致的部分（例如 TP 组内的 dropout mask——同一个被切分的张量，各片上的 mask 必须来自同一个逻辑 mask）用同种子；需要各 rank 不同的部分（数据采样、DP 组间的 dropout）用 `seed + rank` 一类的派生。Megatron-LM 的做法是维护一个独立的 RNG state tracker，在"TP 组内一致"和"全局不同"两个 RNG 状态之间显式切换。**这个规则必须由框架显式实现，不会自动正确**，如果你用的是自研训练框架，这是第一个要审的地方。

关于 A6：这一项值得单独强调，因为它制造的假象最强。断点续训之后的运行与一口气跑完的运行结果不同，很容易被误判成"硬件不确定"，实际上只是 RNG 状态（以及 dataloader 的进度、GradScaler 的 scale 值、优化器的 step 计数）没有被完整存取。排查不可复现时，**第一件事是确认两次运行都是从同一起点一口气跑的**，不涉及任何恢复。

### B. 数据路径

| # | 检查项 | 常见疏漏 |
|---|--------|---------|
| B1 | DataLoader 的 shuffle 由哪个 generator 驱动 | 需要显式传 `generator=`，否则用全局 RNG，受其它代码消耗影响 |
| B2 | `num_workers > 0` 时各 worker 的种子 | **必须设 `worker_init_fn`**。PyTorch 官方文档明确说明：不设时 NumPy 在各 worker 中的随机状态会重复或不可控 |
| B3 | `persistent_workers` / `prefetch_factor` | 不改变数据顺序，但改变 worker 侧 RNG 的消耗时机 |
| B4 | `DistributedSampler.set_epoch()` | 不调用则每个 epoch 的 shuffle 相同；调用方式必须所有 rank 一致 |
| B5 | 文件系统遍历顺序 | `os.listdir` / `glob` 不保证顺序，跨机器可能不同。必须显式排序 |
| B6 | 动态分桶 / packing | 按长度分桶时，桶内顺序依赖排序是否稳定；packing 的拼接顺序可能带随机 |
| B7 | 数据增强与随机 mask | MLM 的随机 mask、随机裁剪、随机替换 |
| B8 | 流式数据源 | 从远端拉取的顺序可能依赖网络，根本不可复现。调试期应切到本地固定数据 |

### C. 模型内部的随机

| # | 检查项 | 备注 |
|---|--------|------|
| C1 | Dropout（含 attention dropout、stochastic depth / drop path） | 调试期直接置 0 是最快的单变量 A/B |
| C2 | MoE 路由 | noisy top-k 的噪声是随机的；即使是确定性 top-k，**gate 分数相同时 `topk` 的平局打破规则是否确定**也要确认 |
| C3 | 权重初始化 | 初始化顺序依赖模块构造顺序；meta device + 延迟初始化会改变时机和顺序 |
| C4 | 采样类算子 | `multinomial` / `randperm` / `bernoulli` |
| C5 | 参数初始化的 RNG 消耗量 | 不同实现消耗的随机数个数不同，会让后续所有 RNG 调用错位。**所以调试期应当从同一个 checkpoint 加载权重，而不是各自初始化** |

### D. 执行层面的不确定性

这一组是真正的难点，也是自研芯片最容易出问题的地方。第四节单独展开。

| # | 来源 | 为什么会不确定 |
|---|------|--------------|
| D1 | 原子操作累加顺序 | `scatter_add` / `index_add` / embedding backward / 任何 reduce 到同一地址的操作。浮点加法不满足结合律，线程完成顺序不同则结果不同。这是 GPU 上最经典的非确定性来源，也正是 `torch.use_deterministic_algorithms` 存在的理由 |
| D2 | 归约树形状 | 同一个 reduce 在不同 block/thread 配置下归约树不同。若 kernel 根据输入大小或当前负载动态选 tiling，同样的输入两次运行可能走不同分支 |
| D3 | 算法自动选择 / autotune | 首次运行测速选最快实现。CUDA 侧对应 `cudnn.benchmark`；**你的栈如果有 kernel autotune 或 JIT 调优缓存，它就是一等的非确定性来源**，而且缓存命中与否还依赖磁盘文件，会表现为"换台机器就不一致" |
| D4 | 集合通信规约顺序 | ring all-reduce 的加法顺序由拓扑决定；若通信库按消息大小或链路状况动态选算法（ring / tree / 双二叉树），两次运行走不同算法则浮点结果不同 |
| D5 | 已知非确定性算子 | PyTorch 官方维护了一份 CUDA 后端的非确定性算子清单。**你的后端需要有自己的清单**，登记在 profile 的 `precision_tools.determinism.known_nondeterministic_ops` |
| D6 | 编译器浮点重排 | fast-math 类优化允许 `(a+b)+c → a+(b+c)`、乘加合并成 FMA（改变舍入次数）、倒数近似代替除法 |
| D7 | 读到未初始化内存 | 表现为"大部分时候对、偶尔不对"，且**一开 dump 就不复现** |
| D8 | 多流写同一块内存 | 缺少 event 同步时写入顺序不定 |

关于 D5 有一条重要提醒：**"开了确定性开关没有抛错"不等于"确定"**。`use_deterministic_algorithms(True)` 的价值有一半在于它会对没有确定性实现的算子**主动抛错**。如果你的后端没有实现这个检查，开关打开只是心理安慰——它既没有切换实现，也没有告诉你哪里不行。

### E. 环境与配置

| # | 检查项 | 备注 |
|---|--------|------|
| E1 | 并行配置（TP/PP/DP 规模） | 变了数值**必然**变，这不是 bug，是不同的计算图。比对必须在相同并行配置下做 |
| E2 | 卡数 | 影响 DP 梯度平均的项数与归约树形状 |
| E3 | 库版本、驱动版本、编译选项 | 记录在 dump 产物的配置指纹里 |
| E4 | GradScaler 的 scale 演化 | scale 是自适应的，一旦某步出现 inf 两次运行就分叉。调试期应改用固定 scale 或切 bf16 |
| E5 | 梯度累积步数与 micro-batch 划分 | 改变累加顺序 |

## 三、没有 dump 工具时能做到哪一步

**能做到的（而且应该先做完这些再去建工具）：**

1. **逐项核对第二节的契约。** 纯检查工作，不需要任何工具。经验上能解决相当比例的案例，尤其是 A6（checkpoint RNG）和 B2（worker 种子）这两条。
2. **单变量 A/B。** 一次只关掉一个随机源——dropout 置 0、`num_workers=0`、关数据增强、固定 GradScaler 的 scale、关 autotune、单卡跑——看是否变确定。这是二分法在配置空间上的应用，每一次的结果都是明确信息。
3. **缩小复现规模。** 层数降到 1~2、batch 降到 1、seq 取最短、单卡、只跑几步。目标是把一次复现压到秒级。**规模缩小后问题消失本身是信息**——它说明问题与规模、并行度或 step 数相关，这直接缩小了嫌疑范围。
4. **判定差异在前向还是反向。** 固定权重只跑前向两次，比 logits。前向就不一致的话，反向根本不用看。这一步只要一个检查点，手工就能做。
5. **粗粒度二分。** 在若干个点手工记录中间量的 norm，用 `print` 即可（因为点数少）。能把首次差异定位到"某几层之间"。

**做不到的：**

- **定位首个差异点到算子级。** 粗粒度二分最多到 module 级，而且每细化一层就要重跑一遍。当一个 step 要几分钟时，这个循环的总成本远超建工具的成本。
- **区分"算子两次输出不同"和"输入已经不同了"。** 没有输入侧的记录，看到输出不同无法归因。这是手工方法最致命的缺陷——你永远不知道看到的是原因还是结果。
- **在多 rank 上同时做。** `print` 在 8 卡上的输出交错且无法自动比对。
- **判定差异的性质。** 是末位 ULP 的舍入顺序差异，还是量级差异？norm 级别的观察分不清，但这两者的处置完全不同（前者正常，后者是 bug）。
- **捕捉低频偶发。** 几百步才一次的话，手工方法的循环成本不可接受，必须有常驻的低开销扫描。

## 四、有工具后的完整流程

前置：确认不涉及 NaN（有的话先去 [NaN/Inf](train-precision-nonfinite.md)），确认两次运行用的是同一份代码、同一配置、从同一 checkpoint 一口气跑完。

1. **建立最小复现。** 缩小到单卡 / 少数层 / batch 1 / 几个 step，确认仍不可复现。若不复现，逐维度放大，**找到使其出现的那个维度**——这个维度本身就是最强的线索。
2. **过一遍第二节契约**，把所有能固定的固定住。
3. **开确定性开关，用校验和模式跑两次。** 确定性场景的判据就是逐位相同，校验和是最合适的摘要形式（理由见[工具栈决策 2](_precision-toolchain.md#决策-2摘要存什么)）。
4. **比对器输出首个不一致的调用实例。** 看的是**首个**，不是数量最多的——下游所有不一致都是它的后果。
5. **对首个不一致点开完整张量 dump，跑两次**，取出两侧的输入和输出。
6. **判定**：

| 观察 | 结论 | 下一步 |
|------|------|--------|
| 输入逐位相同，输出不同 | **算子自身非确定** | 归因到原子加 / 动态归约树 / autotune / 竞态。把该算子单独拿出来做第 7 步 |
| 输入已经不同 | 比对器报的不是真正的首个点 | 该输入来自未被采集的路径（functional 调用、通信、原地修改）。扩大采集范围往上游追 |
| 输入输出都相同，但下游不同 | 中间有未被采集的状态 | 典型是通信、原地修改、或 RNG 状态消耗顺序 |

7. **算子级最小复现。** 固定输入张量，单算子循环跑 1000 次，统计输出的逐位一致率。不是 100% 就实锤了，可以直接交给算子团队，附上输入张量。
8. **通信的单独验证。** 如果嫌疑指向通信：同一份输入在同一组 rank 上反复 all-reduce，比对结果；再把 all-reduce 换成手工的 gather + 单 rank 求和 + broadcast 作为对照。

贯穿全程的一条纪律：**每一步只改一个变量，且每次改完都重新跑满两次。** 不可复现问题的调试最容易犯的错是同时改两处然后发现"好了"，却不知道是哪一处起的作用。

## 五、自研芯片特有的风险点

这五条在成熟的 CUDA 栈上大多已经被解决或有现成工具兜底，在自研栈上需要逐项确认。

**一、算子内部竞态。** SIMT 架构下，同一 block 内线程通过共享内存交换数据时缺少屏障，或跨 block 通过全局内存通信时缺少 memory fence，会产生竞态。症状是"大多数时候对、偶尔差一点，且与输入规模或并发度相关"。对策是 racecheck 类的 sanitizer——[profile](../../hardware-profiles/_TEMPLATE.yaml) 的 `diagnostics.sanitizer` 一节就是为登记这个能力准备的。**如果你的栈还没有 racecheck 等价物，这类问题只能靠反复跑加缩小范围定位，成本极高**，这一项值得单独投入，它的杠杆率不低于 dump 工具本身。

**二、集合通信规约顺序。** 要问清三件事：(a) 固定 rank 数、固定消息大小、固定拓扑下，all-reduce 的加法顺序是否固定；(b) 是否存在基于运行时状况的算法自适应选择；(c) 是否存在"消息被切成多个 chunk、按完成顺序归约"的实现。**第三种最隐蔽**——它在代码上看不出随机性，但 chunk 的完成顺序受链路抖动影响。结论登记在 profile 的 `collective.collective_deterministic`。

**三、编译器浮点重排。** 要问清：默认编译选项是否允许浮点重排；FMA 的生成是否由编译器自行决定；是否有 JIT 且 JIT 决策依赖运行时信息。**autotune 缓存尤其危险**——第一次运行做调优并写缓存，第二次读缓存直接走最优配置，两次运行走的是不同 kernel，数值自然不同，而表面上看你什么都没改。调试确定性问题时必须有办法强制关闭 autotune 或钉死配置。

**四、动态 kernel 选择。** 很多自研栈为了性能按 shape 在多个实现间选择。只要选择逻辑是纯函数（只依赖 shape 和 dtype），就是确定的；一旦依赖设备状态、可用内存、历史统计，就不确定。这一条要看代码而不是看文档。

**五、分配器地址复用掩盖的未初始化读。** 如果某个 kernel 读了未初始化显存，读到什么取决于上一次谁用过这块地址。allocator 的分配顺序在两次相同运行中通常相同，所以**这类 bug 可能看起来是确定的**，直到你改了任何一处分配模式（包括开 dump）才暴露。反过来说，"加了 dump 之后反而不一致了"这个现象要往这个方向想，而不是怀疑 dump 工具有 bug。

另外补一条与 GEMM 相关的：**split-k 实现**会把 K 维切片后分块归约，如果合并由原子加或完成顺序决定，就是不确定的。大 K 的 GEMM 是 LLM 训练的主力算子，这一条的影响面很大，值得专门确认。

## 六、需要你拍板的问题

| # | 问题 | 回答后能解锁 |
|---|------|------------|
| 1 | `torch.use_deterministic_algorithms(True)` 在你的后端上会发生什么——真切换实现、静默忽略、还是遇到无确定性实现时抛错？ | 决定确定性门禁能否成立。静默忽略的话，本文第四节的流程起点要改成"先建这个检查" |
| 2 | 你的通信库在固定 rank 数与消息大小下，all-reduce 是否给出固定的加法顺序？有无运行时算法自适应？ | 能否把通信从嫌疑名单里排除，省掉整条排查分支 |
| 3 | 有没有 kernel autotune / JIT 调优缓存？能否一键关闭或钉死配置？ | 排除两次运行走不同 kernel 配置的可能，这是最容易被忽略的一类 |
| 4 | 默认编译选项是否允许浮点重排与自动 FMA？有没有严格模式？ | 排除编译器层面的数值差异；同时决定[标杆对齐](train-precision-mismatch.md)时误差基线定多少 |
| 5 | 有没有 racecheck 类的竞态检测工具？ | 决定算子内部竞态能被直接检出，还是只能靠统计方法硬碰 |
| 6 | 设备 RNG 的 offset 推进规则是什么？checkpoint 是否保存并恢复设备 RNG 状态？ | 断点续训场景的可复现性，以及能否排除"假性不可复现" |
| 7 | 已知非确定性算子清单有没有？ | 第二节 D 组能否从"要逐个试"变成"照表查" |
