# 并行切分实施

## 一句话结论

**不要自己写一套切分层。** 把模型按 TP / EP / PP 切开这件事，Megatron-LM 和 vLLM 已经写了几万行并经过大规模验证，重写一遍得不到任何差异化。真正需要你投入的是它们底下那一层——**`torch.distributed` 的通信后端**。后端补齐了，上层框架几乎不用改就能跑；后端缺一个算子，上层写得再漂亮也跑不起来。

所以这个领域的建设内容不是「写 skill 教人怎么切」，而是「确认你的通信后端支持到了哪一步」。

## 当前状态

| | |
|---|---|
| 策略选型 | 已建成，见 [model-infer-parallel-analysis](../../skills/model-infer-parallel-analysis/SKILL.md) |
| 切分实现 | 不建议自建，应对接 Megatron-LM / vLLM |
| 卡在哪 | 通信后端的算子覆盖度未知 |
| profile 字段 | `collective.*`、`interconnect.*` |

选型和实施是两件事。选型回答「TP 开多大、要不要 EP」，那是一份可计算的分析，不依赖任何硬件能力，所以已经建成了。实施回答「怎么把它跑起来」，而跑起来的前提在通信库。

---

## 为什么自建切分层是亏本买卖

切分看起来简单——线性层按列切、按行切，加个 all-reduce 就完了。实际做下去会发现，成熟实现里沉淀的大量细节都是一次次踩出来的：

- 列切与行切要配对出现，中间不能插 all-reduce，否则通信量翻倍
- 序列并行要在 all-gather 与 reduce-scatter 之间精确配对，错一个就是精度问题而非报错
- TP 组内 Dropout 的随机数状态要分两套：权重初始化用同步的，激活 Dropout 用各 rank 独立的
- 词表并行的交叉熵要自己实现，不能用框架自带的，否则要把整个 logits 做 all-gather
- MoE 的专家路由在负载不均时要处理容量溢出与丢弃策略
- 从 HuggingFace 权重加载时，不同算子的切分维度不同（`gate_proj` 与 `up_proj` 要按列切并保持拼接顺序，`down_proj` 按行切，注意力的 QKV 融合权重要按头数切而不是按元素数切）

这些逻辑与硬件无关。重写它们唯一的产出是把别人修过的 bug 再修一遍。

**一个例外。** 如果你的芯片有通用生态里没有的硬件能力——最典型的是把集合通信与矩阵计算编进同一个算子（`collective.fused_comm_compute_ops`）——那么为了用上它，确实需要在切分层里改动算子的调用方式。但这是在成熟实现上打一个补丁，不是另起炉灶。

## 真正要确认的是通信后端

上层框架对硬件的全部要求，收敛到一个 `ProcessGroup` 后端实现。下面这张表是按「缺了会死在哪」排的，不是按算子字母序。

| 算子 | 谁需要它 | 缺了的后果 |
|---|---|---|
| `all_reduce` | TP 的行切输出、DP 的梯度规约 | TP 和数据并行都不成立，这是地板 |
| `all_gather` | 序列并行、ZeRO 参数收集、词表并行取 logits | 序列并行与优化器分片不可用 |
| `reduce_scatter` | 序列并行、ZeRO 梯度规约 | 同上。注意它不能用 all_reduce + 切片替代，那样通信量是它的数倍 |
| `broadcast` | 权重分发、采样结果同步 | 启动阶段就会卡住 |
| `barrier` | 初始化同步、调试时核对各 rank 进度 | 多卡调试失去最基本的手段 |
| **`all_to_all_single`（支持不等长切分）** | 专家并行的 token 分发与回收 | **EP 直接不成立** |
| `send` / `recv`（点对点） | 流水线并行传递激活 | PP 不可用 |

**`all_to_all_single` 是最容易被漏掉的那一个。** 很多新栈会优先把 `all_reduce` 做好，因为数据并行训练只需要它。但 MoE 的专家并行需要的是带 `input_split_sizes` / `output_split_sizes` 的不等长 all-to-all——每个 rank 发给其他 rank 的 token 数量在运行时才确定，且各不相同。如果你的后端只有等长版本，EP 这条路就是堵的，而当下主流的大模型大多是 MoE 结构。这一条值得单独去问。

### 算子名之外还要确认的几件事

只看算子列表会漏掉真正的坑。以下每一条都能让「算子都有」的后端在实际跑的时候出问题。

**dtype 覆盖。** 规约类算子对 `bfloat16` 的支持要单独确认。不少早期实现只做了 fp32 和 fp16，bf16 要么不支持要么走软件模拟路径，后者慢得没法用于训练。而现在的大模型训练默认就是 bf16。

**异步与工作句柄。** 集合通信要能返回一个工作句柄（`async_op=True`），让调用方稍后再等待。没有这个，通信与计算的重叠就无从谈起——而重叠是分布式性能的主要来源之一。更隐蔽的是：异步通信必须正确地向 PyTorch 的缓存分配器登记事件，否则通信还在飞、张量的显存已经被分配器回收复用，表现为偶发的数值错误，极难定位。

**子通信域。** 上层框架会为 TP、PP、DP、EP 各建一个子组。一个 TP=8、DP=4 的作业会创建十几个通信域。如果你的后端创建通信域的开销很大，或者数量有上限，启动阶段就会变慢甚至失败。初始化耗时随卡数的增长曲线值得实测。

**非连续张量。** 框架不保证传给集合通信的张量一定是连续的。后端要么支持，要么内部做一次拷贝——但后者是额外开销，应当知情。

**规约顺序的确定性。** 浮点加法不满足结合律，规约顺序不同，结果的最后几位就不同。如果你的实现为了性能采用了运行时可变的规约树，那么同一个作业两次跑出的结果会有细微差异。这会直接导致训练不可复现，参见[训练结果不可复现](train-precision-determinism.md)。这不是 bug，但必须知道，并且最好提供一个可开关的确定性模式。

## 对接路线

按依赖顺序，不按重要性。

**第一步：补齐 `ProcessGroup` 后端。** 这是所有后续工作的前提，且无法绕开。验收标准是通过 PyTorch 自带的分布式测试套件——这套测试覆盖了各算子在不同 dtype、不同张量形状、同步与异步模式下的行为，比自己写的冒烟测试严格得多。

**第二步：让推理框架跑起来。** 推理侧的并行比训练侧简单，只有 TP（和 MoE 的 EP），没有梯度规约和优化器分片。vLLM 的并行逻辑集中在少数几个模块里，接入点清晰。先把推理跑通，能用最小的代价验证后端是否可用。

**第三步：再上训练。** 训练侧要额外处理梯度规约、优化器状态分片、流水线并行的气泡调度，复杂度高一个量级。Megatron-LM 的设备网格抽象是接入点。

**第四步：通信与计算重叠。** 前三步做完是「能跑」，这一步是「跑得快」。需要后端的异步支持，以及通信在独立流上执行。效果验证用[多流并发](../../skills/model-infer-multi-stream/SKILL.md)里的时间窗重叠率方法——流 ID 不同不等于真的并行。

## 验证方法论（现在就能用）

这部分不依赖任何未建设的能力，把后端跑通之后可以直接照做。

**先算子级，再模型级。** 不要用「跑整个模型看 loss 对不对」来验证通信后端。单个集合通信算子写一个最小测试：构造已知输入，手算期望输出，核对每个 rank 拿到的结果。模型级的错误会被几十层的计算摊平，变成「loss 略高」这种无法定位的现象。

**查每个 rank，不只是 rank 0。** TP 的 all-reduce 之后，所有 rank 应该拿到**完全相同**的张量。一个典型 bug 是只有 rank 0 正确、其他 rank 拿到部分规约结果；如果只看 rank 0 的输出，这个 bug 会一路潜伏到精度对齐阶段。断言应当是 rank 间的逐位相等，不是近似相等。

**单卡当标杆做等价性检查。** 同一组权重、同一个输入，TP=1 和 TP=2 的输出应当在 bf16 的容差内一致。有偏差先怀疑切分，不要先怀疑算子。这一步要在性能调优之前做完。

**用加速比反推通信是否正常。** TP 从 1 加到 2，吞吐应当明显上升但达不到两倍（因为引入了 all-reduce）。如果几乎没涨，说明通信代价吃掉了全部收益，要去查互联带宽的实际值而不是标称值；如果反而下降，说明通信走了低效路径（比如本该走片间直连却走了主机内存中转）。

**检查整除性约束。** 切分前先核对：注意力头数能否被 TP 整除、专家数能否被 EP 整除、词表大小能否被 TP 整除（不能整除时需要 padding，而 padding 要和训练时保持一致，否则 embedding 的索引会错位）。这些检查在 [model-infer-parallel-analysis](../../skills/model-infer-parallel-analysis/SKILL.md) 里有完整清单。

## 需要你拍板的问题

| 问题 | 回答后能解锁什么 |
|---|---|
| 你的栈有没有 `torch.distributed` 后端？支持哪些算子？ | 这是整个分布式路线的地板，决定其余问题是否还有意义 |
| 规约类算子支持 `bfloat16` 吗？是原生支持还是软件模拟？ | 决定能否用于现代大模型训练 |
| **有没有支持不等长切分的 `all_to_all_single`？** | 决定 MoE 的专家并行能否跑，这是当前最关键的单点 |
| 集合通信支持 `async_op=True` 并返回工作句柄吗？ | 决定通信与计算能否重叠，影响多卡性能上限 |
| 创建十几个子通信域的开销和上限是多少？ | 决定多维并行组合（TP+PP+DP+EP）能否正常启动 |
| 规约顺序是否确定？有没有可开关的确定性模式？ | 决定分布式训练能否复现 |
| 有没有通信与计算融合的算子？ | 有的话值得在切分层打补丁用上，这是你相对通用生态的差异化点 |
| 你打算先上推理还是先上训练？ | 决定先对接 vLLM 还是 Megatron-LM |
