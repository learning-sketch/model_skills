# 推理性能拆解

把一份 kernel 时间线变成「下一步该改哪里」的结论。

分析本身与硬件无关——算的都是时间区间的聚合与交叠。与硬件相关的只有两件事：你的 profiler 产物长什么样，以及它有没有硬件计数器。前者由[适配层](../../tools/profiler_adapter/README.md)吸收，后者决定能不能做受限类型判定。

## 硬件依赖

本技能从 `hardware-profiles/` 下的 active profile 读取硬件信息。若字段为 `null` 或 `_status` 为 `unknown`/`assumed`，先提示用户确认再执行。

| profile 字段 | 用途 | 缺失时的降级行为 |
|---|---|---|
| `profiler.kernel_table_columns` | CSV 格式的列名映射 | 若输入是 chrome trace 则不需要；否则要求用户用 `--column` 手工指定 |
| `profiler.task_type_values` | 区分计算 / 通信 / 显存搬运 | 退化为按 kernel 名称模式猜测，通信识别率下降，气泡分析会把通信算进计算 |
| `profiler.hardware_counters.*` | 判定访存受限还是计算受限 | 受限类型一律报「未知」。**不要猜**，缺计数器时按耗时排序给建议即可 |
| `profiler.hardware_counters.memory_bound_threshold` | 受限判定阈值 | 用默认值 0.6，并在报告中说明这是默认值而非实测标定 |
| `devices.models[].memory_bandwidth_gb_s` | 估算理论下限、算带宽利用率 | 跳过理论对比，只做相对分析 |
| `devices.models[].compute.*` | 同上 | 同上 |

## 适用场景

- 有一份 profiler 产物，需要定位性能瓶颈
- 做完一次优化，需要验证是否真的变快、以及快在哪
- 两次运行性能不同，需要找出差异来源
- 怀疑存在 step 间抖动

## 不适用场景

- 还没采集到性能数据 → 先解决采集，见 [性能数据采集的建设说明](../../docs/pending/perf-profiling.md)
- 精度问题 → 本技能只看时间，不看数值
- 要分析计算图结构、找融合机会 → 见 [图结构与融合机会分析](../../docs/pending/graph-fusion-analysis.md)
- 单卡显存不足 → 这是容量问题不是性能问题

## 工作流

### Step 0：归一化输入

任何分析之前，先把 profiler 产物转成统一 schema。**不要直接解析原始产物**——那样写出来的分析只能用于一种 profiler。

```bash
cd tools
python -m profiler_adapter.normalize \
  --input <profiler 产物路径> \
  --format auto \
  --profile ../hardware-profiles/<你的芯片>.yaml \
  --output /tmp/kernels.jsonl
```

转换完会自动打印校验报告。**先读报告再往下走**，它会告诉你这份数据能做哪些分析、哪些做不了。

常见的报告结论与处置：

| 报告提示 | 含义 | 处置 |
|---|---|---|
| `没有 step 标注` | 采集时没调 profiler 的 step() | 只能整体分析，看不了 step 间抖动。需要抖动分析的话重新采集 |
| `缺少访存利用率计数器` | 采集时没开硬件计数器 | 受限类型判不了。若 profiler 支持，重采；不支持则跳过 Step 4 的受限判定 |
| `只有一个流` | 数据里只有单流 | 跳过 Step 3 |
| `有 N 条事件 duration 为 0` | 时间精度不足或解析错位 | 占比小可忽略；占比大说明列映射错了，回头检查 profile |
| 通信占比为 0 但你明知有多卡 | 通信 kernel 没被识别出来 | 用 `--comm-pattern` 补充你的通信库 kernel 命名模式 |

### Step 1：整体节奏

```bash
python -m profiler_adapter.analyze --input /tmp/kernels.jsonl --analysis summary
```

看三件事，按顺序：

**第一，先排除冷启动。** 首个 step 通常显著慢于其余，原因是算子库初始化、显存池预热、图编译。这是正常现象。**所有后续统计都应剔除首步**，否则均值会被带偏。如果是第二、三步仍慢，才值得查。

**第二，看气泡占比。** 气泡是墙钟里设备上一个 kernel 都没在跑的时间。

| 气泡占比 | 判读 | 下一步 |
|---|---|---|
| < 5% | 设备基本喂饱了 | 瓶颈在 kernel 本身，去 Step 4 |
| 5% ~ 20% | 存在下发或同步开销 | 查是否有主机侧同步、小算子过多、是否可以上图模式 |
| > 20% | 设备大量空等 | 优先解决喂数问题，优化单个 kernel 收益很小 |

气泡大的常见原因，按排查成本从低到高：主机侧存在 `.item()` / `.cpu()` 之类的强制同步；单步内 kernel 数量过多导致下发跟不上执行；数据加载或预处理在关键路径上；存在跨设备拷贝未异步化。

**第三，看 step 间离散。** 报告会点名偏离中位数 20% 以上的 step。排除首步后仍有离群，往往是真实抖动——可能来自通信等待、显存碎片触发的重新分配、或与其他负载竞争。

### Step 2：耗时去向

```bash
python -m profiler_adapter.analyze --input /tmp/kernels.jsonl --analysis bucket
```

内置了一套通用分桶规则（注意力、矩阵乘、归一化、激活、专家路由、通信、逐元素）。**如果「其他」桶占比超过 10%，说明规则不匹配你的 kernel 命名**，需要自定义：

```bash
cat > /tmp/buckets.json <<'EOF'
{
  "注意力": "你的 attention kernel 命名模式",
  "专家计算": "你的 MoE kernel 命名模式",
  "通信": "你的通信 kernel 命名模式"
}
EOF
python -m profiler_adapter.analyze --input /tmp/kernels.jsonl \
  --analysis bucket --bucket-rules /tmp/buckets.json
```

规则按声明顺序匹配，先命中先归属。所以要把更具体的规则写在前面。

判读要点：

- **逐元素桶占比高**（比如超过 15%）通常意味着有融合机会。大量小的逐元素算子说明计算图没有被充分融合
- **通信桶占比高**要结合 Step 3 一起看。通信耗时长本身不是问题，被完全藏进计算里就不是问题；暴露在关键路径上才是
- **注意力与矩阵乘的比例**反映模型结构特征。长序列下注意力占比升高是预期的；短序列下注意力占比异常高，查是否 mask 构造或 attention 实现有问题

### Step 3：并行是否真实生效

仅当数据里有多条流时才需要这一步。

```bash
python -m profiler_adapter.analyze --input /tmp/kernels.jsonl --analysis overlap
```

**这一步的存在理由是一个反直觉的事实：把算子挂到不同的流，只是声明了「可以并行」，不等于真的并行了。** 实际能否并行取决于数据依赖、资源竞争和调度策略。只看代码改没改、流 ID 对不对，判断不了这件事，必须看时间窗是否真的重叠。

重叠率用「较短那条流的忙时」做分母——要回答的问题是「这条流有没有被藏进另一条里」。用总时长做分母会把本来就无法重叠的部分算进去，低估效果。

| 重叠率 | 结论 | 处置 |
|---|---|---|
| ≥ 50% | 有效并行 | 优化生效，保留 |
| 5% ~ 50% | 部分重叠 | 有效果但不充分。查是否有多余的同步点、或两段工作量本身不匹配 |
| < 5% | 几乎未重叠 | **这是假并行**。流切了但没起作用，改动应当回退或重做 |

假并行的常见原因：两段工作之间存在未被识别的真实数据依赖；同步点插得过早，把本可重叠的部分切断了；两段工作竞争同一种硬件资源，调度器只能串行；其中一段的工作量太小，启动开销就把窗口吃光了。

### Step 4：定位具体 kernel

```bash
python -m profiler_adapter.analyze --input /tmp/kernels.jsonl --analysis top --top 20
```

输出按总耗时排序。注意是**总耗时**不是单次耗时——一个单次 5us 但被调用一万次的小算子，比一个单次 500us 只调一次的大算子更值得优化。

两列需要解释：

**离散度**是同一个 kernel 多次执行的耗时变异系数。超过 0.3 说明这个 kernel 执行时间不稳定。同样的输入形状下耗时波动大，通常意味着它受到了外部干扰——资源竞争、缓存命中率波动、或者它实际上在等别的东西。

**受限类型**基于硬件计数器判定，没有计数器时一律报「未知」。判定逻辑：

| 访存利用率 | 计算利用率 | 判定 | 优化方向 |
|---|---|---|---|
| 高 | 低 | 访存受限 | 减少数据搬运：融合相邻算子、提高数据复用、考虑预取、降低精度 |
| 低 | 高 | 计算受限 | 减少计算量：量化、稀疏化、换更高效的算法 |
| 低 | 低 | 两者都低 | **这类最值得查**。通常不是算子本身的问题，而是并行度不足、启动开销占主导、或在等同步 |
| 高 | 高 | 混合 | 已接近硬件上限，优化空间有限 |

「两者都低」配合 `block_dim` 一起看：如果并行度远小于设备的计算单元数量，说明这个 kernel 根本没把设备喂满，应该增大批量或合并调用，而不是去优化 kernel 内部。

### Step 5：优化前后对比

同一套流程跑两遍，分别产出 JSON，再比：

```bash
python -m profiler_adapter.analyze --input /tmp/baseline.jsonl --json > /tmp/before.json
python -m profiler_adapter.analyze --input /tmp/optimized.jsonl --json > /tmp/after.json
```

对比时注意三条纪律：

1. **两次采集的条件必须一致**——同样的输入长度、批量、并行配置、step 范围。有一项不同，对比就不成立
2. **剔除首步后再比**
3. **看绝对值不要只看百分比**。某个桶降了 50% 听起来很好，但如果它只占总耗时的 2%，整体只快了 1%

判断优化是否成功，至少要满足其中两条：目标 kernel 耗时下降；整体墙钟缩短；气泡占比没有变大；其他桶没有出现明显劣化。只有目标 kernel 变快而整体没变快，说明瓶颈不在那里，这次优化方向选错了。

## 输出要求

完成分析后必须报告：

1. **数据可信度**：采集了几个 step、剔除了哪些、校验报告里有哪些字段缺失、因此哪些结论无法给出
2. **整体结论**：墙钟、气泡占比、是否存在 step 间抖动
3. **耗时去向**：各桶占比，以及「其他」桶的占比（用于说明分桶规则是否可信）
4. **瓶颈定位**：Top kernel 列表，每条给出受限类型；无计数器时明确说明这是按耗时排序而非受限分析
5. **优化建议**：每条建议必须指明依据来自上面哪一项数据，并给出预期影响的量级
6. **未解决的疑问**：数据无法回答的问题，以及要回答它们需要补采什么

不要给没有数据支撑的建议。如果数据不足以得出结论，说「需要补采什么」比编一个合理的猜测有价值。

## 知识来源

- 时间区间合并与交叠计算：标准算法，无特定来源
- 气泡（设备空闲）与墙钟的区分：GPU 性能分析的通用概念，见 NVIDIA Nsight Systems 公开文档对 GPU utilization 的定义
- roofline 式的访存受限 / 计算受限判定：Williams, Waterman, Patterson, "Roofline: An Insightful Visual Performance Model for Multicore Architectures" (2009)
- 变异系数用于识别执行抖动：通用统计方法
- chrome trace 事件格式：Chrome Trace Event Format 公开规范，以及 PyTorch `torch.profiler` 的公开导出行为
- 首步剔除、对比实验控制变量：性能测试的通用工程实践
