# 多流并行优化

把设备上互不依赖的工作排到不同的流上同时跑。**挂到不同流只是必要条件，不是并行本身**——本技能一半的篇幅用于证明它真的并行了。

## 硬件依赖

本技能从 `hardware-profiles/` 下的 active profile 读取硬件信息。若字段为 `null` 或所在大节的 `_status` 为 `unknown` / `assumed`，**先提示用户确认再执行**，不要按 CUDA 语义自行推定。

| profile 字段 | 用途 | 缺失时的降级行为 |
|---|---|---|
| `pytorch.api.stream_class` | 创建流 | 阻塞。没有流就没有本技能 |
| `pytorch.api.stream_context` | 在指定流上下发算子 | 阻塞 |
| `pytorch.api.event_class` | 建立跨流依赖 | 阻塞。只有流没有事件时，唯一的跨流同步手段是全设备同步，那会抹掉全部收益 |
| `pytorch.api.record_stream` | 跨流使用张量时防止被提前回收 | **高危降级**。该字段为 `null` 时不得使用"分配流与消费流不同"的编排，必须改用显式保活（见 Step 5），否则会产生偶发数据损坏 |
| `pytorch.api.synchronize` | 计时与收尾 | 阻塞 |
| `pytorch.device_namespace` | 所有设备 API 前缀；也用于查 `current_stream` / `default_stream` / `wait_stream` 等 profile 未逐项登记的流 API | 这几个 API **profile 未登记**，需向用户确认其等价名，不得臆造 |
| `vendor.architecture_class` | 决定哪些优化手段成立（见 Step 6 的架构前提） | 按 `SIMT` 保守处理并标注假设 |
| `devices.models[].compute_units.count` | 判断两个 kernel 是否有共存的算力空间，解释"切了流仍串行" | 跳过算力占用判定，假并行只能靠 profiler 现象倒推 |
| `profiler.api` | 采集时间线 | **本技能的验证环节失效**。没有 profiler 不得宣称优化成功，只能给出端到端墙钟对比，并明确标注"未验证是否真重叠" |
| `profiler.kernel_table_columns.stream_id` | 确认 kernel 落在哪条流 | 无法区分"没切流"与"假并行"，五类分诊退化为三类 |
| `profiler.kernel_table_columns.start_time_us` / `duration_us` | 计算重叠率 | 重叠率无法计算，本技能的核心判据失效 |
| `profiler.kernel_table_columns.name` / `task_type` + `profiler.task_type_values.*` | 区分计算 / 通信 / 拷贝 kernel | 只能按 kernel 名字人工归类 |
| `collective.torch_backend` / `collective.primitives` | 通信计算重叠场景的可用原语 | 通信重叠场景跳过 |
| `collective.fused_comm_compute_ops.available` | 若为真，优先用融合算子而不是手工多流 | 按 `false` 处理，走手工重叠 |
| `interconnect.intra_node.bandwidth_gb_s` | 估算通信耗时，判断重叠的理论收益上限 | 收益上限无法预估，只能实测 |
| `kernels.moe.*` | MoE 双流场景的算子可用性 | MoE 场景需用户说明实际调用了哪些算子 |
| `kernels.memory.host_offload_api` | KV cache 异步卸载的拷贝接口 | 卸载场景跳过 |
| `graph.graph_capture.constraints.collective_ops_supported` | 图模式与多流叠加时，通信能否同时满足两边约束 | 不建议叠加，先单独验证多流 |

**profile 未覆盖但本技能需要的能力**（见文末「已知的 profile 缺口」）：硬件执行队列数量、流优先级支持、拷贝引擎数量与计算/拷贝并发能力、`current_stream` / `default_stream` / `wait_stream` 的等价 API、pinned 主机内存分配接口、捕获期多流支持、profiler 能否导出硬件队列（而非软件流 ID）。这些缺一项就会削弱对应的判定能力，须在报告中声明。

> **架构前提，务必先读**：「按流限制计算核数量」「给某条流划一块算力」这类手段，在 SIMT 架构上**没有一等公民 API**。它预设了计算单元可以被细粒度地划分给不同的流。如果 `profile` 里没有登记对应能力，**不要建议用户这么做，也不要在方案里假设它存在**。SIMT 上可用的只有流的并发下发与（若支持）流优先级。

## 适用场景

- 已有性能基线，且 profiling 显示单步时延中存在**互不依赖**的工作（典型：通信与计算、拷贝与计算、MoE 的共享专家与路由专家）
- 存在明显的设备空窗：某段时间只有通信在跑、计算单元闲着，或反之
- MoE 模型，dispatch/combine 的通信占比高
- 有 KV cache 卸载、权重换入换出等后台数据搬运需求

## 不适用场景

| 现象 | 应转向 |
|---|---|
| 单步时延几乎全被一个大算子占满 | 算子级优化。多流无处可并 |
| 瓶颈是主机下发开销（设备有大量空窗但都是碎片化的 gap） | `model-infer-graph-mode`。多流不消除下发开销，反而增加主机侧负担 |
| eager 下结果就不对 | `model-infer-runtime-debug` |
| 要决定 TP/PP/EP 怎么切 | 并行策略分析。本技能只在给定切分下做重叠 |
| `profile.collective.fused_comm_compute_ops.available` 为真 | 优先用融合算子，比手工多流更稳、收益更高 |
| 没有 profiler | 可以做，但**不能宣称成功**。见硬件依赖表 |

## 工作流

### Step 0 — profile 门禁

读 `pytorch.api.stream_class` / `event_class` / `stream_context` / `record_stream` 与 `profiler.*`。任一"阻塞"项为 `null` 即停止并询问。`record_stream` 为 `null` 时在后续全程禁用"跨流分配-消费"编排。

### Step 1 — 整网 DAG 拆解

**输入**：模型代码或框架的执行路径。
**动作**：画出一次完整前向的粗粒度 DAG，节点取到"一个模块"的粒度，并在每个节点上标注四个属性。

```
输入 → 嵌入 → [Decoder Layer × N] → 末层归一化 → 输出头 → 采样 → 后处理
                      ↑
                 展开见 Step 2
```

| 节点属性 | 取值 | 用途 |
|---|---|---|
| 类型 | 计算 / 集合通信 / 点对点通信 / 主机设备拷贝 / 主机侧逻辑 | 不同类型占用不同硬件资源，决定能否真并行 |
| 耗时占比 | 从 profiler 取 | 只对占比高的节点找并行机会，低于总时延 5% 的节点不值得折腾 |
| 输入来源 | 依赖哪些上游节点 | Step 3 的依赖判定输入 |
| 是否触及共享可变状态 | KV cache / 随机数状态 / 通信域 / 分配器 | 状态依赖的识别依据 |

**同时标出三类特殊点**，它们是重叠机会的高发区，也是隐式同步的高发区：
- 集合通信点（TP 的 all-reduce、EP 的 all-to-all）
- 主机设备交互点（采样结果回传、调度决策、`.item()`）
- 数据搬运点（KV cache 卸载/换入、权重换页）

### Step 2 — Decoder Layer 内部拆解

稠密层与 MoE 层分开画。

**稠密层**：
```
h → 归一化 → QKV 投影 → 位置编码 → 注意力(读写 KV cache) → 输出投影 → [TP all-reduce] → 残差
  → 归一化 → gate/up 投影 → 激活 → down 投影 → [TP all-reduce] → 残差
```

**MoE 层**：
```
h → 归一化 ─┬→ 路由打分 → token 重排 → [EP all-to-all dispatch] → 分组矩阵乘 → [EP all-to-all combine] → 还原重排 ─┐
            └→ 共享专家（稠密前馈）───────────────────────────────────────────────────────────────────────────┘ → 相加 → 残差
```

MoE 层的这个分叉是**结构性的并行机会**：共享专家与路由专家分支的输入相同、输出相加，彼此之间没有任何数据依赖。记下这一点，Step 4 要用。

### Step 3 — 依赖分类与可并行性判定

对 DAG 中每一对候选节点，逐类判定。**四类依赖的处置方式完全不同，不要混为一谈**。

| 依赖类型 | 定义 | 识别方法 | 判定 |
|---|---|---|---|
| **数据依赖** | B 的输入张量是 A 的输出 | 看 DAG 的边 | **必须串行**。除非把 A 切块让 B 分块消费（流水化），否则没有商量余地 |
| **状态依赖** | A、B 不传数据，但读写同一份可变状态：同一块 KV cache、随机数生成器状态、同一个通信域、同一个显存池 | 看节点属性里标的共享状态 | 默认**串行**。要并行必须先把状态拆开（各用各的缓冲区）或证明访问区间不相交（例如写 KV cache 的不同 token 位置） |
| **事件依赖** | 没有内在依赖，顺序完全由代码里的同步原语决定 | 看代码里的 event / stream 等待 | **可重排**。这正是编排的自由度所在。注意：有些事件依赖是历史遗留的过度同步，删掉即可获得并行 |
| **集合通信顺序依赖** | 同一通信域内的集合通信，**所有 rank 必须以相同顺序进入** | 列出每个 rank 上集合通信的调用序列 | **全局顺序必须一致**。可以把通信放到专门的流上，但不得让不同 rank 的相对顺序发生变化，否则死锁或结果错乱。多条流上同时发同一通信域的集合通信是高危写法 |

**判定输出表**（每个候选对一行）：

| 候选对 | 数据依赖 | 状态依赖 | 事件依赖 | 通信顺序依赖 | 结论 |
|---|---|---|---|---|---|
| 共享专家 vs 路由专家分组矩阵乘 | 无 | 无 | 无 | 无 | **可并行候选** |
| 注意力 vs 同层前馈 | 有（前馈吃注意力输出） | — | — | — | 串行 |
| 当前层 all-reduce vs 下一段计算 | 有 | — | — | 有 | **改写后可并行**：把计算切块，与通信分块流水 |
| KV cache 卸载拷贝 vs 后续层计算 | 无（卸载的是已完成的历史块） | 有（同一 KV 缓冲区，但区间不相交） | — | — | **可并行候选**，需证明区间不相交 |
| 微批 0 的注意力 vs 微批 1 的前馈 | 无（不同微批） | 有（KV cache 按微批分区） | — | — | **可并行候选** |

只有结论为"可并行候选"或"改写后可并行"的才进入 Step 4。

### Step 4 — 为每个并行点给出至少两种编排方案

**要求**：每个并行点必须给 ≥2 套方案并说明取舍。只给一套的方案往往是想当然，比较过才知道约束在哪。每套方案描述五项：流的分配、事件的位置、额外显存开销、预期收益、风险。

#### 场景 A：MoE 共享专家与路由专家双流

| | 方案 A1：共享专家下沉副流 | 方案 A2：通信独立成流 |
|---|---|---|
| 流分配 | 主流跑路由分支全程；副流跑共享专家 | 主流跑计算（路由分组矩阵乘 + 共享专家）；通信流跑 dispatch/combine |
| 事件 | 分叉处主流 record，副流 wait；相加前主流 wait 副流 | dispatch 发出后 record，分组矩阵乘前 wait；combine 同理 |
| 额外显存 | 共享专家的中间激活需与路由分支共存 | 通信缓冲需双份（发送中的不能被覆盖） |
| 预期收益 | 上限 = min(共享专家耗时, 路由分支耗时) | 上限 = min(通信耗时, 可重叠的计算耗时) |
| 风险 | 共享专家与分组矩阵乘都是算力密集型，可能互相抢不到算力而退化为串行（见 Step 6 第三条） | 通信顺序依赖：必须保证各 rank 顺序一致 |

**取舍**：若 profiling 显示分组矩阵乘已接近占满计算单元，A1 大概率无收益，优先 A2（通信与计算抢的是不同资源，更容易真重叠）。

#### 场景 B：通信与计算重叠

| | 方案 B1：分块流水 | 方案 B2：跨层预取式重叠 |
|---|---|---|
| 做法 | 把输出投影按输出维切成 K 块，第 i 块算完立刻发起其 all-reduce，同时算第 i+1 块 | 把本层通信与**下一层**中不依赖该通信结果的计算（如下一层的权重相关准备、另一微批的计算）重叠 |
| 流分配 | 计算流 + 通信流 | 同左 |
| 事件 | 每块一对 record/wait，共 K 对 | 层边界处一对 |
| 额外显存 | K 块的分片缓冲 | 需要同时持有两层的中间结果 |
| 预期收益 | 理想情况隐藏 (K-1)/K 的通信时间 | 取决于下一层有多少独立工作，通常少于 B1 |
| 风险 | K 太大则每块的 kernel 太小、通信包太小，效率反而下降；K 太小则重叠不足。需扫 K | 跨层改造侵入性大；通信顺序依赖更难保证 |

**取舍**：K 的取值从 2、4、8 扫起，看 Step 6 的重叠率与端到端时延共同选。注意通信包变小后带宽利用率下降，用 `profile.interconnect.intra_node.bandwidth_gb_s` 估算单块通信是否还在高效区间。

#### 场景 C：KV cache 异步卸载

| | 方案 C1：拷贝流 + 事件 | 方案 C2：双缓冲 |
|---|---|---|
| 做法 | 卸载拷贝下发到独立拷贝流，计算流继续；需要时等事件 | 两块缓冲区交替，一块在被计算读、另一块在被拷贝写 |
| 额外显存 | 低 | 多一块缓冲 |
| 风险 | **张量生命周期**：被拷贝的源张量若在计算流上分配并释放，分配器可能在拷贝完成前复用该块。必须用 `{{profile.pytorch.api.record_stream}}`（CUDA 参考: `Tensor.record_stream`）或显式保活 | 同左，且需保证缓冲切换与事件对齐 |
| 前置条件 | 主机侧需为页锁定内存，否则拷贝会退化为同步。**pinned 内存分配接口 profile 未登记，需向用户确认**；且需确认设备是否支持计算与拷贝并发（拷贝引擎数量 profile 未登记） | 同左 |

#### 场景 D：微批流水

把一个 batch 切成 2 个微批，让微批 0 的注意力与微批 1 的前馈交错。方案差异在切分点（层级交错 vs 模块级交错）与微批数（2 个还是更多）。**代价**：KV cache 与激活需按微批分区，显存上升；微批太小则每个 kernel 变小、算力利用率下降。只在单步时延确实有空窗时才做。

### Step 5 — 实现纪律

```python
# 占位符均来自 profile，注释里的 CUDA 名仅供对照，不要直接使用。
Stream = {{profile.pytorch.api.stream_class}}     # CUDA 参考: torch.cuda.Stream
Event  = {{profile.pytorch.api.event_class}}      # CUDA 参考: torch.cuda.Event
on     = {{profile.pytorch.api.stream_context}}   # CUDA 参考: torch.cuda.stream

# 取当前流的 API，profile 未登记（CUDA 参考: torch.cuda.current_stream），需向用户确认
main_stream = CURRENT_STREAM_API()
side_stream = Stream()
done_main, done_side = Event(), Event()

# 1) 主流产出分叉点的输入
h = norm(x)
done_main.record()                 # 在主流上打点

# 2) 副流必须先等主流把 h 写完，否则读到未初始化数据
with on(side_stream):
    done_main.wait()               # 跨流等待，不是全设备同步
    y_side = shared_expert(h)
    # h 在主流分配、在副流消费 —— 必须登记，否则主流释放后分配器可能立刻复用
    h.record_stream(side_stream)   # 名称取自 {{profile.pytorch.api.record_stream}}
    done_side.record()

# 3) 主流跑另一分支
y_main = routed_experts(h)

# 4) 合并前等副流
done_side.wait()
out = y_main + y_side
# y_side 在副流分配、在主流消费 —— 同样要登记
y_side.record_stream(main_stream)
```

**四条纪律**：

1. **跨流等待用事件，不用全设备同步**。`{{profile.pytorch.api.synchronize}}` 会把所有流排空，一次调用就能抹掉全部重叠收益。它只应出现在计时代码和进程收尾处
2. **凡是"在流 A 分配、在流 B 使用"的张量，都要登记**。缺了这一步的错误是偶发的、压力越大越容易出现，极难定位（见 Step 7 第 5 类）
3. **`record_stream` 为 `null` 时改用显式保活**：把跨流张量放进一个列表，直到消费流上的事件被主流等到之后再清空列表。这是语义更弱但更通用的兜底
4. **多卡下，集合通信的下发顺序在所有 rank 上必须一致**。把通信挪到专用流不改变这一要求

### Step 6 — 验证：重叠率

**这是本技能的核心判据。没做这一步的"多流优化"一律视为未完成。**

**为什么必须做**：把算子挂到不同的流，只表示它们**被允许**并发执行，不表示它们**真的**同时在设备上跑。软件层的流 ID 与设备上的实际执行是两回事，中间隔着隐式同步、硬件队列数量、以及算力占用三道关。

**物理并行的三个必要条件**（缺一不可）：

1. 两个 kernel 在不同的流上（软件层，看 `profile.profiler.kernel_table_columns.stream_id`）
2. 两者的执行时间窗在设备时间线上确实重叠（看 `start_time_us` 与 `duration_us`）
3. 两者合计没有占满设备资源。若 kernel A 的并行度已经铺满全部计算单元（`profile.devices.models[].compute_units.count`），B 只能等 A 的任务退出才能上——表现为"切了流但时间窗首尾相接"。这解释了为什么"大矩阵乘 + 大矩阵乘"双流通常无收益，而"通信/拷贝 + 计算"、"小 kernel + 大 kernel"有收益

**重叠率计算方法**：

```
输入：profiler kernel 表（统一 schema），取一个稳态 decode step 作为时间窗 [T0, T1]
步骤：
  1. 按 stream_id 分组，取目标两条流 A、B
  2. 对每条流，把其 kernel 的 [start_time_us, start_time_us + duration_us] 区间求并集
     （求并集不是求和：同一条流上若有重叠或空隙，求和会算错）
     得 busy_A、busy_B（并集总长）
  3. overlap_us = len( union(A) ∩ union(B) )
  4. overlap_pct = overlap_us / min(busy_A, busy_B)
     —— 以较短的一方为分母，含义是"短的那条有多少被长的那条盖住了"
  5. 另算一个端到端指标：
     speedup_potential = (busy_A + busy_B) / (T1 - T0)
     大于 1 说明确实有并发发生
```

**分档阈值与判读**（这是工程经验的建议默认值，可按你的负载调整，但调整后要在报告中写明）：

| `overlap_pct` | 判读 | 动作 |
|---|---|---|
| < 10% | **没有真并行** | 转 Step 7 分诊第 2、3 类。不要在这个状态下讨论收益 |
| 10% ~ 40% | **弱重叠** | 通常是事件位置偏保守（等得太早），或一方工作量太少。检查事件能否后移；检查两条流的 `busy` 是否严重不对称 |
| 40% ~ 70% | **部分重叠**，已有实际收益 | 可继续优化编排；若端到端已达标可以收手 |
| > 70% | **接近理想** | 短的一方基本被完全隐藏，剩余空间很小 |

**重叠率只是中间指标，端到端才是结论**。必须同时记录：

| 指标 | 判据 |
|---|---|
| 单步时延（稳态中位数） | 下降幅度 < 3% 视为落在噪声带内，等于无收益，应回退 |
| 理论收益上限 | `min(busy_A, busy_B) / (T1 - T0)`。实际收益显著低于上限时，说明编排还有空间 |
| 显存峰值 | 多流会让更多缓冲共存，必须记录增量 |
| 输出正确性 | 见 Step 7 第 1 类。多流最危险的失败模式是**结果错但不报错** |

### Step 7 — 五类问题分诊

出问题时先对号入座，不要乱改。

| # | 症状 | 根因 | 定位方法 | 修复 |
|---|---|---|---|---|
| 1 | **结果不对**（稳定错或偶发错） | 依赖写错：消费方没等生产方，读到了未写完的数据 | 在怀疑点插一次全设备同步。**加同步后结果就对了 = 确认是依赖问题**，这是最干净的判据 | 补事件：生产流 record、消费流 wait。不要用全设备同步当修复，那等于放弃多流 |
| 2 | **没真切流** | 算子根本没下发到目标流 | profiler 里看 `stream_id`：目标 kernel 与主流同号 | 常见原因：下发代码不在流上下文内；某些算子/库内部固定使用默认流；通信库的通信有自己的内部流。逐个确认，无法改变的就换编排方案 |
| 3 | **假并行**（流切对了但不重叠） | 时间窗首尾相接 | `stream_id` 不同，但 `overlap_pct` < 10% | 三查：(a) 中间有隐式同步——显存分配、`.item()`、缓存清理、同步拷贝、profiler 自身的采集点；(b) 算力已被占满（条件 3），换成"异构资源"配对，如通信/拷贝配计算；(c) 硬件执行队列数不足导致多条软件流被映射到同一队列——**该上限 profile 未登记，需向用户确认** |
| 4 | **真重叠但无收益** | 重叠发生了，端到端没变 | `overlap_pct` 高但单步时延降幅 < 3% | 三查：(a) 重叠的那段不在关键路径上（占总时延比例本就很低）；(b) 被隐藏的一方太短，省下的时间可忽略；(c) 两条流互抢资源导致主路径自身变慢——对比两条流各自的 `busy` 与单流基线，若主路径的 `busy` 变长了就是这一类，应回退 |
| 5 | **偶发数值错误或非法内存访问**，压力越大越频繁 | **跨流张量生命周期**：张量在流 A 上分配，交给流 B 使用；A 侧的 Python 引用释放后，显存分配器认为该块在 A 上已空闲，立刻把它分配给 A 上的新张量，而 B 还在读它 | 症状强相关于并发压力与 batch 大小；关掉多流开关即消失；加全设备同步即消失 | 对每一个跨流使用的张量调用 `{{profile.pytorch.api.record_stream}}`（CUDA 参考: `Tensor.record_stream`）。该 API 不可用时，用 Step 5 纪律 3 的显式保活列表。**这是多流最隐蔽的一类 bug，务必在 code review 清单里逐个张量过一遍** |

### Step 8 — 开关与回退（强制）

多流优化必须可一键关闭，没有例外。

- [ ] 提供显式开关（配置项或环境变量），命名体现作用范围（例如区分 MoE 双流与通信重叠两个独立开关），默认值由用户决定
- [ ] 开关关闭时走的单流路径**必须是原来那条代码路径**，而不是"多流代码只用一条流"——后者保留了全部事件同步，回退不彻底，也验证不出基线
- [ ] 启动时日志打印每个开关的生效状态
- [ ] 回退路径纳入日常测试。长期不走的分支必然腐坏
- [ ] 文档记录：每个开关对应哪个并行点、实测收益多少、在什么条件下建议关闭（例如小 batch 下收益为负时）

## 输出要求

完成后必须汇报：

1. **DAG 拆解结果**：整网与 Decoder Layer 两级，标注各节点类型与耗时占比
2. **依赖判定表**：所有候选对的四类依赖判定与结论，含被判为串行的（说明为什么不能并）
3. **编排方案对比**：每个并行点 ≥2 套方案的五项描述，以及最终选型理由
4. **重叠率实测数据**：每个并行点的 `busy_A`、`busy_B`、`overlap_us`、`overlap_pct`、落在哪一档、以及使用的时间窗定义
5. **端到端收益**：单步时延变化（含是否超过 3% 噪声带）、显存峰值增量、理论上限与实际收益的差距
6. **正确性验证**：与单流基线的输出比对结果；跨流张量的生命周期处理清单（逐个张量列出用了 `record_stream` 还是显式保活）
7. **开关清单**：开关名、默认值、对应并行点、建议关闭的条件
8. **残留风险**：因 profile 字段缺失而无法确认的项（硬件队列数、拷贝引擎并发、流优先级等）、`_status` 为 `assumed` 的字段、以及明确声明"未使用任何需要按流划分算力的手段"

## 已知的 profile 缺口

`_TEMPLATE.yaml` 当前没有以下字段，而本技能的对应步骤需要它们。遇到时**向用户确认，不要臆造**，并把确认结果建议补进 profile。

| 建议字段路径 | 本技能哪一步要用 | 没有时的替代做法 |
|---|---|---|
| `pytorch.api.current_stream` / `default_stream` / `wait_stream` | Step 5 的全部编排代码。`pytorch.api` 只登记了 `stream_class` / `event_class` / `stream_context` / `record_stream`，缺了"取当前流"和"流等流" | 只能用事件做所有等待，代码更啰嗦；取当前流无替代，必须问用户 |
| `devices.models[].hardware_queue_count` | Step 7 第 3 类假并行的根因 (c)。多条软件流最终映射到几条硬件队列 | 无法解释"流切对了但不重叠"，只能逐个排除其他原因 |
| `devices.models[].copy_engine_count` / `compute_copy_concurrent` | 场景 C 的可行性前提。拷贝能否与计算真正并发 | 卸载方案只能实测，做完才知道有没有用 |
| `pytorch.api.pin_memory` | 场景 C。页锁定主机内存的分配接口，不用它则拷贝退化为同步 | 卸载场景大概率无收益，需标注未验证 |
| `pytorch.api.stream_priority_supported` | Step 4 的编排细化。能否让关键路径的流优先获得下发机会 | 不使用优先级，编排自由度降低 |
| `profiler.kernel_table_columns.hardware_queue_id` | Step 6 的重叠率。软件流 ID 与硬件队列不是一回事，只看软件流可能高估并发 | 重叠率按软件流计算，在队列复用时会偏乐观，需在报告中声明 |
| `graph.graph_capture.constraints.multi_stream_supported` | 多流与图模式叠加 | 不叠加，先各自单独验证 |
| `devices.models[].stream_compute_partitioning` | 判断"按流划分算力"是否存在 | **按不存在处理**。该字段缺失时不得提出任何需要给流分配固定算力份额的方案 |

## 知识来源

本技能的方法论全部来自公开技术资料与通用工程实践，不含任何厂商专有信息：

- **NVIDIA 公开文档**：CUDA Programming Guide 的 Streams and Concurrency 章节（流的并发语义、事件同步、隐式同步的触发条件、kernel 并发执行需要资源有空余这一前提）、CUDA C++ Best Practices Guide 关于异步拷贝与页锁定内存的说明
- **PyTorch 官方文档**：CUDA semantics 中的流语义与 `record_stream` 说明、显存缓存分配器按流记账的行为描述（这正是第 5 类问题的成因）、`torch.distributed` 关于集合通信在所有 rank 上须同序调用的要求
- **Megatron-LM 等开源训练/推理框架的公开实现**：张量并行中通信与计算的分块重叠、微批流水的组织方式，以及其公开文档中关于并发通信通道数量限制的讨论
- **MoE 系统的公开论文与开源实现**：共享专家与路由专家的结构（DeepSeekMoE 类设计）、专家并行 all-to-all 与分组矩阵乘的流水重叠（DeepEP 等开源库的公开设计说明）
- **vLLM / FlashInfer 等开源推理项目的公开实现**：KV cache 分块管理与异步搬运的工程做法
- **通用性能工程方法**：区间并集计算重叠率、关键路径分析、以噪声带为阈值判定收益是否显著
